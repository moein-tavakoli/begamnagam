# راهنمای اجرای محلی و عملیات

این راهنما برای demo محلی است. Compose عمداً `DEBUG=1` و `DEMO_MODE=1` را ثابت نگه می‌دارد؛ صرف تغییر `.env` آن را به سرویس واقعی تبدیل نمی‌کند. پورت‌ها روی `127.0.0.1` هستند و نباید بدون تکمیل فاز انتشار به اینترنت باز شوند.

## گردش‌کار روزمره UI

با backend فعال روی localhost:8000، از ریشه `make dev-ui` را اجرا کنید. این فرمان فقط `npm run dev` است و Next.js Fast Refresh را فعال می‌کند؛ ذخیرهٔ فایل تغییر را در مرورگر اعمال می‌کند. `npm ci` فقط در نصب اول یا تغییر lockfile لازم است.

اگر frontend کانتینری پورت۳۰۰۰ را گرفته است، `docker compose stop frontend` بزنید و بقیه سرویس‌ها را روشن نگه دارید. اگر frontend نیتیو در حالت `next start` اجرا می‌شود، همان پردازش را یک بار متوقف و با `make dev-ui` جایگزین کنید. هنگام ویرایش‌های بعدی سرور را restart نکنید و image نسازید. تغییر متغیرهای محیط/پیکربندی ممکن است restart یک‌باره بخواهد.

SW فقط در production ثبت می‌شود؛ سناریوهای نصب و آفلاین را در بررسی انتشار جدا اجرا کنید. این کار نیازی به ساخت image در هر ویرایش UI ایجاد نمی‌کند. [راهنمای رسمی Fast Refresh](https://nextjs.org/docs/architecture/fast-refresh) و [فرمان next dev](https://nextjs.org/docs/app/api-reference/cli/next) مبنای این گردش‌کارند.

در نسخه۰٫۳٫۲، رفت‌وبرگشت یک متغیر CSS آزمایشی در مرورگر با ثابت‌ماندن `performance.timeOrigin` تأیید شد؛ صفحه reload و image ساخته نشد. تغییر آزمایشی برگشت داده شد. ۱۰ تست فرانت و typecheck نیز موفق بودند. فایل تولیدی `next-env.d.ts` از Git خارج شده و `npm run typecheck` ابتدا `next typegen` را بدون build تولیدی اجرا می‌کند.

## شروع کامل demo

از ریشهٔ مخزن:

```sh
python3 scripts/init-local.py
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 300
python3 scripts/smoke.py
```

نصب اول به دریافت image و dependency نیاز دارد؛ دانلود پیش از زمان انتظار سلامت انجام می‌شود. `--wait` سلامت سرویس‌ها را پس از بالا آمدن بررسی می‌کند. migration در سرویس یک‌باره انجام می‌شود و backend پس از موفقیت آن شروع می‌شود. worker و beat پس از سلامت backend فعال می‌شوند. در هر محیط فقط یک beat برای این پروژه اجرا کنید.

```sh
docker compose ps
docker compose logs --tail=100 backend worker beat frontend
```

`make up`، `make logs`، `make smoke` و `make down` میان‌بر همین کارها هستند. `.env` فقط یک بار ساخته می‌شود؛ کلیدهای آن و volumeهای پایگاه داده را با هم نگه دارید. تغییر کلید رمزنگاری بدون مهاجرت، شماره‌های قدیمی را ناخوانا می‌کند؛ تغییر کلید HMAC تطبیق شماره و توقف دریافت را می‌شکند.

## محیط سبک بدون Docker

برای توسعهٔ سریع، بک‌اند بدون `DATABASE_URL` از SQLite، بدون `REDIS_URL` از حافظهٔ همان فرایند و بدون broker از اجرای eager استفاده می‌کند. این حالت برای توسعه و تست واحد است و رفتار قفل‌ها و صف واقعی را اثبات نمی‌کند.

```sh
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.lock.txt
cd backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

در ترمینال دیگری، از ریشه:

```sh
cd frontend
npm ci
npm run dev
```

سپس رابط روی `http://localhost:3000` است. `frontend/.env.example` تنظیم `INTERNAL_API_URL` و متغیرهای SEO را توضیح می‌دهد. برای اجرای نیتیو، نمونه را به `frontend/.env.local` کپی کنید یا متغیرهای لازم را در محیط همان پردازش export کنید؛ `make dev-ui` فایل `.env` ریشهٔ Compose را خودکار وارد محیط Next نمی‌کند. در dev پس از تغییر تنظیم محیط، dev server را یک بار restart کنید. در خروجی standalone، rewrite و خروجی SEO هنگام build ثبت می‌شوند؛ بعد از تغییر مقصد API، `APP_BASE_URL` یا `SEO_INDEXABLE` دوباره frontend را build کنید. برای تست PostgreSQL و RabbitMQ از Compose استفاده کنید.

## تنظیم SEO و انتشار

`APP_BASE_URL` مبدأ یکتای canonical، Open Graph، JSON-LD و sitemap فرانت و نشانی لینک‌های گیرنده در بک‌اند است؛ این دو بخش باید یک مبدأ هماهنگ داشته باشند. `SEO_INDEXABLE=0` پیش‌فرض است: demo محلی، CT خصوصی و staging باید `noindex` بمانند و sitemap خالی باشد. robots خواندن HTML را مجاز می‌گذارد تا crawler بتواند `noindex` را ببیند؛ مسیرهای API/admin منع می‌شوند. فقط پس از مجوز انتشار عمومی، با دامنهٔ واقعی HTTPS، مقدار۱ مجاز است؛ این متغیر هیچ provider یا استقراری را فعال نمی‌کند.

Compose توسعه هر دو مقدار را هنگام ساخت image فرانت می‌فرستد. در Compose داخلی/انتشار که image آماده می‌گیرد، باید همان image با build argهای درست ساخته شده باشد؛ تغییر `.env.internal` / `.env.release` در زمان اجرا، metadata، robots و sitemap آماده را اصلاح نمی‌کند. برای دستور ساخت و بررسی مسیرهای عمومی/خصوصی، [راهنمای SEO](seo.md) را دنبال کنید. این بررسی انتشار جدا از حلقهٔ روزمرهٔ Hot Reload است.

نمونه‌های URL و رمز در `.env.example` مخصوص محلی‌اند. Compose متغیرهای کاوه‌نگار بالا را از `.env` به backend، migrate، worker و beat منتقل می‌کند؛ فرانت به آن‌ها دسترسی ندارد. اعتبارنامه‌ها پیش‌فرض خالی‌اند و افزودن کلید، حالت demo یا شبکهٔ خاموش را تغییر نمی‌دهد. در اجرای مستقیم Django، باید متغیرها را به محیط پردازش وارد کنید؛ فایل `.env` خودکار بارگذاری نمی‌شود. کلید را در URL مرورگر، لاگ، مخزن یا متغیر `NEXT_PUBLIC_*` قرار ندهید.

از نسخه۰٫۸٫۲، مسیر OTP کاوه‌نگار پیش‌فرض `sms/send` است. متن ثابت شامل نام سرویس، کد شش‌رقمی و اعتبار۵دقیقه‌ای است؛ ورودی آزاد کاربر وارد آن نمی‌شود. شمارهٔ خط از `KAVENEGAR_SENDER` گرفته می‌شود و `hide=1` ارسال می‌شود. در پاسخ نامعلوم، ارسال خودکار تکرار نمی‌شود و کد در API یا لاگ نمایش داده نمی‌شود. پس از تأیید الگو می‌توان `KAVENEGAR_OTP_MODE=lookup` و `KAVENEGAR_OTP_TEMPLATE` را تنظیم کرد؛ الگوی خالی در حالت lookup رد می‌شود. ارسال عادی تابع محدودیت خط و شماره‌های مسدود اپراتور است؛ تحویل به همهٔ شماره‌ها تضمین نمی‌شود.

تنظیم‌های غیرآزمایشی ناقص، در startup رد می‌شوند؛ کلاینت provider پیاده و با HTTP fixture آزموده شده است؛ پذیرش خارجی و فعال‌سازی همچنان باز است. برای تنظیمات جداگانه انتشار از `deploy/release.env.example` و برای پیش‌نیازهای فعال‌سازی و rollback از [runbook۰٫۷](release-v0.7/RUNBOOK.fa.md) استفاده کنید. مشخصات API مرجع در [مستندات رسمی کاوه‌نگار](https://kavenegar.com/rest.html) آمده است.

### تست محلی OTP واقعی، با پرداخت و پیام آزمایشی

نسخه۰٫۸٫۳ مسیر مستقلی با مجوز صریح کارفرما دارد. در `.env` خصوصی، `OTP_BACKEND=kavenegar` و `LOCAL_REAL_OTP_ENABLED=1`، کلید/خط واقعی، `KAVENEGAR_OTP_MODE=sms`، هش شماره خود در `OTP_TEST_RECIPIENT_HASHES` و بودجه‌ها لازم‌اند. هش با `core.privacy.digest(core.privacy.normalize_phone(phone))` در محیط سرور و کلید HMAC همان محیط ساخته می‌شود؛ هش شمارهٔ خام SHA256 یا کلید محیط دیگر معتبر نیست. شمارهٔ خام و کد را در فایل یا لاگ نگه ندارید.

برای این تست، `DEMO_MODE=1`، `SMS_BACKEND=console`، `PAYMENT_BACKEND=demo`، `PROVIDER_NETWORK_MODE=disabled` و `LIVE_PROVIDERS_ENABLED=0` اجباری‌اند. مبدأ برنامه باید loopback باشد. فقط متد OTP به مقصد ثابت `https://api.kavenegar.com` اجازه دارد؛ متد عمومی ارسال، استعلام SMS و زرین‌پال همچنان بسته‌اند. redirect دنبال نمی‌شود. تغییر پرداخت یا پیام به provider واقعی در این حالت startup را متوقف می‌کند.

سقف اولیهٔ تست خصوصی `PROVIDER_DAILY_BUDGET_RIAL=100000` (۱۰هزار تومان) و `OTP_MAX_COST_RIAL=10000` (هزار تومان) است؛ این‌ها سقف‌های محافظه‌کارانه‌اند، نه تعرفهٔ کاوه‌نگار. حداکثر۱۰رزرو کامل روزانه در بودجه جا می‌گیرد؛ سقف۳درخواست در۱۰دقیقه برای هر شماره و محدودیت نشست/CSRF نیز برقرار است. در هزینهٔ بیش از رزرو، کنترل هزینه ارسال‌های بعدی را متوقف می‌کند. رزرو قبلی/سقف ثبت‌شدهٔ پایین‌تر ممکن است ظرفیت باقی‌مانده را کمتر کند.

تنظیمات پس از شروع پردازش ثابت‌اند؛ بعد از تغییر `.env` فقط بک‌اند را با محیط جدید دوباره اجرا کنید. UI با `make dev-ui` و Fast Refresh فعال می‌ماند؛ image نسازید. از bootstrap یا health مقدار `otp_is_real=true` را بررسی کنید؛ هیچ شماره یا کلیدی در این پاسخ نیست. سپس در فرم ورود، شمارهٔ خود را وارد و «دریافت کد تأیید» را بزنید. تحویل واقعی فقط با دریافت روی گوشی بررسی می‌شود و از تست خودکار نتیجه نمی‌گیریم.

بازگشت: `LOCAL_REAL_OTP_ENABLED=0` و `OTP_BACKEND=demo`؛ سپس فقط بک‌اند را دوباره اجرا کنید. برای تغییر حالت، چالش‌های استفاده‌نشدهٔ قبلی را مصرف‌شده علامت بزنید تا کد قبلی مبنای تست تازه نشود. `python3 scripts/smoke.py` در حالت OTP واقعی، پیش از درخواست هر کد متوقف می‌شود؛ برای smoke ابتدا به demo برگردید. پایلوت و benchmark مصنوعی این استثنا را در پردازش جدا خاموش می‌کنند.

### خطای گواهی در پایتون محلی

اگر `ssl.get_default_verify_paths().cafile` خالی است و اتصال کاوه‌نگار با `SSLCertVerificationError` شکست می‌خورد، در اجرای نیتیو macOS می‌توان `SSL_CERT_FILE=/etc/ssl/cert.pem` را در `.env` خصوصی گذاشت؛ فایل باید CA معتبر سیستم باشد. پایتون آن را هنگام ساخت context امن می‌خواند. این مسیر میزبان را داخل کانتینر منتقل نکنید؛ Linux از CA خودش استفاده می‌کند. تأیید گواهی و نام میزبان را خاموش نکنید. نمونهٔ عمومیِ بدون کلید `https://api.kavenegar.com/v1/0/utils/getdate.json` برای بررسی TLS کافی است و پیامک نمی‌فرستد. مرجع: [SSL پایتون](https://docs.python.org/3/library/ssl.html#ssl.create_default_context).

از نسخه۰٫۸٫۴، شکست تأیید گواهی/DNS/رد اتصال پیش از ارسال با HTTP503 برمی‌گردد و چالش غیرقابل استفاده می‌شود. timeout یا پاسخ نامعلوم همچنان چالش را نگه می‌دارد، `delivery_status=unknown` برمی‌گرداند و خودکار تکرار نمی‌شود. خطای قطعی را با پذیرفته‌شدن پیامک یکی نگیرید. لاگ سرور فقط request ID و علت محدود و امن مثل `tls_certificate_verification_failed` یا پذیرش provider را ثبت می‌کند؛ متن خام خطای شبکه/URL کلیددار، شماره، کد و ورودی خصوصی ثبت نمی‌شود. دو رزرو آزمایشی قبلی با خطای TLS، محافظه‌کارانه در سقف روز باقی ماندند.

سقف روزانهٔ فعلی، حداکثر۵سفارش ساخته‌شده در ۲۴ ساعت گذشته است؛ سفارش پرداخت‌نشده یا لغوشده نیز حساب می‌شود تا رزرو مکرر باعث مزاحمت نشود. رزرو گیرنده تا۱۵دقیقه برای سفارش پرداخت‌نشده و تا تعیین نتیجه برای سفارش در صف فعال است. فاصلهٔ سراسری گیرنده و همان جفت فرستنده/گیرنده هردو۲۴ساعت‌اند؛ روز تقویمی و نیمه‌شب ملاک نیست. این کنترل‌ها در PostgreSQL و زیر قفل اعمال می‌شوند؛ کش، مبنای یکتای شمارش نیست. تست‌ها را با Redis database 15 اجرا کنید تا پاک‌کردن کش تست روی محدودیت‌های نمونهٔ در حال اجرا اثر نگذارد.

### ریست محدودیت برای تست ادمین

از نسخه۰٫۸٫۹، هر شمارهٔ تأییدشده یک‌بار۳ارسال رایگان دارد. migration0010 به حساب‌های موجود هم۳واحد می‌دهد و سفارش‌های قبلی را تغییر نمی‌دهد. مانده در فهرست حساب‌های ادمین فقط خواندنی است. ریست محدودیت آزمایشی، سهمیهٔ هدیه را شارژ نمی‌کند. پردازش `expire_unpaid_orders` رزروهای رایگان منقضی‌شده را آزاد می‌کند؛ beat/worker باید روشن باشند. سفارش رایگان تراکنش مالی ندارد، ولی اگر روزی ارسال واقعی با مجوزهای قبلی فعال شود هزینهٔ provider و سقف بودجه همچنان اعمال می‌شوند. وضعیت نامعلوم سهمیه را تا تعیین تکلیف نگه می‌دارد.

در محیط محلی، پس از migration، `DEMO_TEST_TOOLS_ENABLED=1` را در `.env` قرار دهید و پردازش‌های بک‌اند را یک بار با env جدید اجرا کنید. در این workspace فعال شده است. فرانت توسعه با Hot Reload روشن می‌ماند.

۱. در `/admin/` وارد حساب مدیر شوید و از بخش حساب‌ها، «ریست محدودیت آزمایشی» را باز کنید؛ مسیر مستقیم `/admin/core/account/test-limits/` است.
۲. شمارهٔ فرستنده‌ای که قبلاً در محصول وارد شده، شمارهٔ گیرندهٔ تست و دلیل کوتاه را وارد کنید. ارقام فارسی/عربی یکسان‌سازی می‌شوند.
۳. «ریست محدودیت برای تست» را بزنید و در محصول پیش‌نمایش تازه بسازید. شمارش۵سفارش فرستنده و فاصلهٔ سراسری گیرنده و همان جفت از زمان ریست شروع می‌شوند. پس از ارسال تازه، محدودیت دوباره برقرار است؛ ریست، حالت نامحدود دائمی نیست.

مدیر کل این مجوز را دارد؛ staff دیگر به `core.reset_demo_limits` و برای دیدن لینک فهرست حساب‌ها به مجوز مشاهدهٔ حساب نیاز دارد. GET تغییری نمی‌دهد و POST به CSRF نیاز دارد. سابقهٔ ریست در «ریست‌های محدودیت آزمایشی» و OperatorAudit ثبت می‌شود؛ شمارهٔ خام یا متن پیام در رکورد ریست ذخیره نمی‌شود.

ابزار فقط با `DEMO_MODE=1`، `SMS_BACKEND=console`، `PAYMENT_BACKEND=demo`، `PROVIDER_NETWORK_MODE=disabled` و `LIVE_PROVIDERS_ENABLED=0` کار می‌کند. در سایر حالت‌ها، هم ریست تازه ممنوع است و هم ریست‌های قبلی در شمارش نادیده گرفته می‌شوند. با خاموش‌کردن ابزار، شمارش عادی بر اساس سابقه برمی‌گردد. قطع دریافت، تعلیق، ارسال به خود، سفارش باز، ورود OTP و بودجهٔ پیامک تغییری نمی‌کنند. گیرندهٔ دارای سفارش باز باید ابتدا تعیین تکلیف شود؛ این ابزار سفارش، پرداخت یا وضعیت تحویل را حذف یا بازنویسی نمی‌کند. هیچ پیامک یا پرداختی با کلیک ریست انجام نمی‌شود.

### تنظیم ارسال و لحن هر حساب از نسخه۰٫۸٫۱۲

در `/admin/core/account/` حساب محصول خودت را از روی شمارهٔ پوشیده پیدا کن و شناسهٔ آن را باز کن. حساب محصول باید قبلاً با OTP ساخته شده باشد؛ ورود مدیر به‌تنهایی فرستندهٔ محصول نمی‌سازد. دو تیک مستقل در صفحهٔ حساب وجود دارند:

- **ارسال نامحدود برای تست:** سقف۵سفارش در۲۴ساعت، فاصلهٔ۲۴ساعتهٔ گیرنده/جفت و محدودیت کوتاه‌مدت preview/order برای همین فرستنده نادیده گرفته می‌شوند. لازم نیست پس از هر ارسال ریست بزنی. سفارش باز همان گیرنده باید تمام شود؛ ارسال بعدی را پس از رسید آزمایشی انجام بده.
- **لحن صریح‌تر و محترمانه:** پیام‌های خروجی همین حساب از مجموعهٔ متن‌های واضح‌تر انتخاب می‌شوند. مثلاً «بوی بدن شما در جمع محسوس است. لطفاً برای رفع آن، به شست‌وشوی بدن و تعویض لباس بیشتر توجه کنید.» حالت پیش‌فرض سایر حساب‌ها همچنان ملایم است. این تیک مربوط به فرستنده است و دریافت‌کننده را قضاوت یا دسته‌بندی نمی‌کند.

دلیل کوتاه تغییر را بنویس و ذخیره کن. تغییر هر تیک با مدیر، شناسهٔ حساب، مقدار قبل/بعد و دلیل در OperatorAudit ثبت می‌شود؛ شماره و متن خصوصی وارد این سابقه نمی‌شوند. مدیر کل مجاز است. staff دیگر برای دیدن حساب به `view_account` و برای هر گزینه به‌ترتیب به `core.manage_test_sending` یا `core.manage_message_tone` نیاز دارد؛ این مجوزها خودکار به گروه‌های پشتیبانی داده نمی‌شوند. GET تغییری ایجاد نمی‌کند و POST به CSRF نیاز دارد. شماره، هویت، تعلیق و اعتبار هدیه در این فرم قابل ویرایش نیستند.

تیک نامحدود فقط وقتی اثر دارد که تمام شروط ابزار آزمایشی بالا برقرار باشند. در محیط واقعی یا با خاموش‌شدن ابزار، حتی مقدار ذخیره‌شدهٔ true هم نادیده گرفته می‌شود؛ فعال‌کردن آن در آن محیط رد می‌شود و خاموش‌کردنش همیشه با مجوز ممکن است. غیرفعال‌کردن تیک، محدودیت عادی را فوراً بر اساس تاریخچه برمی‌گرداند؛ تاریخچه حذف یا ریست نشده است. این گزینه فقط محدودیت تعداد/فاصله را برمی‌دارد و سهمیهٔ۳ارسال رایگان را افزایش نمی‌دهد؛ ارسال‌های بعدی همچنان مسیر پرداخت آزمایشی دارند.

قطع دریافت، ارسال به خود، تعلیق/حذف حساب، سفارش باز گیرنده، کنترل محتوای ممنوع، توقف اضطراری، محدودیت OTP، کنترل کلی سیل درخواست IP و شروط هزینه/provider برقرارند. این تنظیم هیچ پیامک واقعی یا پرداختی را فعال نمی‌کند. برای تست این قابلیت، ریست بودجه یا OTP لازم نیست.

متن صریح هم پیش از تأیید به فرستنده نمایش داده می‌شود و پس از تأیید ثابت می‌ماند. تغییر تیک لحن، متن preview یا سفارش موجود را عوض نمی‌کند؛ برای دیدن لحن تازه پیش‌نمایش تازه بساز. فیلتر توهین/تهدید/اطلاعات خصوصی قبل و بعد از انتخاب متن برقرار است؛ مدل محلی هم فقط می‌تواند از متن‌های بررسی‌شدهٔ همان لحن انتخاب کند و اجازهٔ ارسال متن آزاد ندارد.

## مدل محلی اختیاری

برای مسیر پیش‌فرض، هیچ مدل یا GPU لازم نیست. اگر Ollama را از قبل روی دستگاه اجرا می‌کنید، `AI_MODE=ollama` و `OLLAMA_MODEL` را به مدلی که واقعاً نصب دارید تنظیم کنید. مقدار URL پیش‌فرض Compose به میزبان Docker اشاره می‌کند. برای دسترسی کانتینر، سرویس باید از شبکهٔ Docker قابل دسترس باشد؛ پورت مدل را عمومی نکنید.

```sh
docker compose up -d --force-recreate backend worker beat
```

مدل فقط موضوع و متن ورودی را می‌بیند؛ شماره تلفن در درخواست مدل نیست. خروجی به شناسهٔ یکی از متن‌های بررسی‌شده محدود می‌شود. قطعی یا پاسخ نامعتبر مدل باعث توقف پیش‌نمایش می‌شود. اجرای موفق این آداپتور با مدل نصب‌نشده ادعا نمی‌شود؛ تست پاسخ‌های ساختگی جای تست کیفیت مدل واقعی را نمی‌گیرد.

Celery با صف‌های event/control از نوع exclusive و پیام‌های task پایدار کار می‌کند. `acks_late` و `reject_on_worker_lost` فعال‌اند؛ outbox و قفل دیتابیس از پردازش تکراری دفاع می‌کنند. در RabbitMQ4.4 قابلیت منسوخ transient non-exclusive را فعال نکنید. اگر پس از ارتقا صف متوقف شد، image بک‌اند و worker را با هم بازسازی کنید.

## صف و رفع اشکال

| نشانه | بررسی |
| --- | --- |
| رابط باز می‌شود اما API خطا دارد | سلامت backend و مقصد rewrite؛ سپس مقدار `CSRF_TRUSTED_ORIGINS` |
| خطای CSRF پس از ورود | بازخوانی bootstrap و cookie جدید؛ مسدودنبودن cookie و یکسان‌بودن hostname مرورگر |
| سفارش در صف می‌ماند | سلامت RabbitMQ و worker، اجرای beat و outbox؛ دوباره پرداخت نکنید |
| پیام دوم پذیرفته نمی‌شود | سقف فرستنده و فاصله گیرنده؛ API علت خصوصی گیرنده را اعلام نمی‌کند |
| `migrate` ناموفق است | log همان سرویس و سلامت PostgreSQL؛ backend تا موفقیت migration شروع نمی‌شود |
| تغییر مقصد API اثر ندارد | build دوبارهٔ frontend؛ rewrite در build ثبت شده است |
| canonical یا robots دامنه/حالت قبلی را دارد | `APP_BASE_URL` و `SEO_INDEXABLE` را هنگام build فرانت اصلاح کنید؛ تغییر env زمان اجرای image آماده کافی نیست |
| پس از تعویض رمز DB اتصال قطع است | رمز role موجود داخل volume خودکار با تغییر env عوض نمی‌شود؛ از راه تغییر رمز DB با حفظ داده استفاده کنید |
| `address pools have been fully subnetted` یا تداخل subnet | شبکهٔ پروژه صریح تنظیم شده است؛ در صورت تداخل با شبکه یا VPN خود، `DOCKER_SUBNET` را به یک محدودهٔ خصوصی آزاد تغییر دهید |

تست دود رکوردهای آزمایشی با شماره‌های تولیدشده می‌سازد و به جای پاک‌کردن دادهٔ کاربر، داده‌های خودش را باقی می‌گذارد. این تست فقط loopback و demo را می‌پذیرد.

## پشتیبان، بازیابی و عملیات نسخه۰٫۷

volume داده با `docker compose down` حذف نمی‌شود؛ برای توقف عادی از `down -v` استفاده نکنید. backup ساده SQL بدون رمز دیگر مسیر پیشنهادی نیست. ابزار `scripts/backup-restore.py` پشتیبان رمز‌شده0600 و restore فقط به DB تازه می‌سازد. کلید backup و کلید application جدا و خارج مخزن نگه داشته شوند. [راهنمای کامل](release-v0.7/RUNBOOK.fa.md) و [شاهد restore](release-v0.7/RESTORE.json) را دنبال کنید.

`python manage.py bootstrap_roles` نقش‌های حداقلی را بدون انتساب افراد می‌سازد؛ `ops_snapshot` شاخص‌های جمعی می‌دهد؛ `prune_private_data --dry-run` و `rotate_encryption` ابتدا بازبینی و سپس با دستور apply اجرا می‌شوند. HMAC شماره را بدون مهاجرت تغییر ندهید. `release_readiness --human-checks <path> --require-live-ready` موارد ناقص/انسانی را با exit غیرصفر رد می‌کند و مجوز انتشار صادر نمی‌کند.

## CI و اجرای محلی از GitHub

`ci.yml` روی push و PR بررسی بک‌اند و فرانت و یک چرخهٔ Compose را اجرا می‌کند. actionها به commit مشخص قفل شده‌اند؛ imageهای زیرساخت به شاخهٔ نسخه قفل هستند و patch آن‌ها ممکن است به‌روز شود. برای انتشار واقعی باید digest image و برنامهٔ به‌روزرسانی آسیب‌پذیری نیز ثبت شود.

`local-deploy.yml` فقط دستی و روی `main` اجرا می‌شود. runner باید مورد اعتماد، Linux و دارای Docker باشد و برچسب `begamnagam-local` داشته باشد. اجرای PR ناشناس روی آن مجاز نیست. `clean: false` کلید محلی را حفظ می‌کند؛ این workflow به محیط production یا ابر آروان متصل نیست. آزمون‌ها روی ماشین محلی اجرا می‌شوند؛ نتیجهٔ GitHub تا زمان push و اجرای workflow تأییدشده نیست.

## لینک کوتاه لغو در پیامک۰٫۸٫۱۳

در پیش‌نمایش تازه، آدرس بدون `https://` و با کد۸حرف/عدد ساخته می‌شود. APP_BASE_URL را همچنان HTTPS معتبر تنظیم کنید؛ scheme فقط هنگام ساخت متن پیامک حذف می‌شود و TLS، cookie و CSRF تغییری نمی‌کنند. پیام و لینک قدیمی با snapshot قبلی باقی می‌مانند. لینکِ ارسال‌شده بعد از پذیرش فعال می‌شود؛ همان صفحهٔ `/r` با fragment کوتاه کار می‌کند و migration یا تنظیم تازه لازم نیست.

برای تست، با حساب مصنوعی یک سفارش آزمایشی بسازید، سپس لینک را باز کنید؛ GET نباید دریافت را قطع کند. اقدام توقف نیازمند کلیک و POST با CSRF است. دریافت خودکار لینکِ بدون scheme روی گوشی واقعی هنوز پذیرش انسانی می‌خواهد. raw link و کد را وارد لاگ/تحلیل نکنید. محدودیت۱۲۰در۱۰دقیقهٔ IP علاوه بر۳۰در۱۰دقیقهٔ نشست و کد اعمال می‌شود. در CT، فقط peer پراکسی مشخص برای IP واقعی اعتماد می‌شود؛ XFF ورودی دلخواه را اعتماد نکنید.

برای rollback، نسخهٔ قدیمی۰٫۸٫۱۲ به‌تنهایی کدهای۸نویسه‌ای را قبول نمی‌کند. مسیر recipient را با پذیرش هر دو قالب نگه دارید؛ بازگشت کور به validator قدیمی، لینک‌های تازه را می‌شکند. کد۸نویسه‌ای و snapshot قبلی را بازنویسی نکنید؛ راه ایمن، اصلاح رو به جلو یا backport پذیرش هر دو قالب است.
