# راهنمای اجرای محلی و عملیات

کیف پول در `/wallet` و کنترل کیف پول/زرین‌پال در تنظیمات `/manage` اضافه شده‌اند. هر دو کلید به‌صورت پیش‌فرض خاموش‌اند؛ کد جدید اعتبار نمونه ایجاد نمی‌کند و پروفایل هدیهٔ واقعی، پرداخت پولی را همچنان بسته نگه می‌دارد. پیش از راه‌اندازی پرداخت، [راهنمای کیف پول و تطبیق مالی](wallet.fa.md) را بخوانید. فروش تازه فقط بسته‌ای است: کیف پول برای خرید بسته و زرین‌پال برای خرید بسته یا شارژ کیف پول. پرداخت مستقیم هر پیام مسدود است؛ verify و برگشت هزینهٔ پرداخت‌های قبلی مستقل از کلیدهای ادمین ادامه دارند. سوابق آزمایشی در بخش خرید محصول واقعی نمایش یا ادامه داده نمی‌شوند؛ رسیدگی تاریخی مدیر در محیط متناظر باقی است.

پنل Next.js در `/manage` با حساب کارکنان فعلی قابل استفاده است؛ داشبورد عملیات، فهرست‌های محصول و تغییر محدودیت‌ها را با همان مجوزها و سوابق جنگو ارائه می‌کند. جزئیات در [راهنمای پنل مدیریت](management.fa.md) است. انتشار این کد روی سرور به دستور صریح تازه نیاز دارد.

## برنچ‌ها و انتقال به prod

از ۲۰۲۶-۱۰-۲۹ فقط دو برنچ `dev` و `prod` نگه داشته می‌شوند. هر دو از commit
`0321acf454a26d2daf07051c953d8264cecf1b34` ساخته شدند و پس از بررسی برابری
تاریخچه، برنچ قبلی `codex/product-mvp` در مخزن محلی و GitHub حذف شد.
`dev` برنچ پیش‌فرض مخزن و محل تمام تغییرات بعدی است:

```sh
git switch dev
git pull --ff-only origin dev
```

تغییرهای معنادار را در `CHANGELOG.md` زیر `Unreleased` ثبت کنید. برای انتشار،
ابتدا نسخه و شواهد را روی `dev` تکمیل و push کنید، سپس pull request با مبدأ
`dev` و مقصد `prod` بسازید. حفاظت `prod`، pull request و موفقیت بررسی‌های
`backend`، `frontend` و `compose` روی مبنای به‌روز را لازم می‌کند و برای مدیر
مخزن هم برقرار است؛ force-push و حذف آن بسته‌اند. بررسی‌ها فقط از داده و
provider آزمایشیِ جدا استفاده می‌کنند. پس از موفقیت CI، از روش **Create a merge commit** برای انتقال استفاده کنید تا تاریخچهٔ مشترک دو برنچ حفظ شود. پس از merge،
`dev` و `prod` را حذف نکنید. squash/rebase تاریخچهٔ انتشار را جدا می‌کند؛ در
شروع دور بعد، merge انتشار را به `dev` برگردانید:

```sh
git fetch origin
git switch dev
git merge --ff-only origin/prod
git push origin dev
```

هیچ push یا merge، استقرار خودکار سرور را اجرا نمی‌کند؛ استقرار فقط با درخواست
صریح کارفرما برای همان تغییرها و مطابق راهنمای نسخهٔ جاری انجام می‌شود.
`local-deploy.yml` صرفاً demo جدا روی runner محلی مورد اعتماد است و فقط با
اجرای دستی از `dev` فعال می‌شود؛ مسیر استقرار محصول واقعی نیست.

## تنظیم دستی محدودیت‌های جاری

در ادمین، «تنظیمات محدودیت‌های سایت» (`/admin/core/sitelimits/1/change/`) تعداد و بازهٔ ارسال هر فرستنده، تعداد دریافت از مجموع پیام‌ها و دعوت‌ها، فاصلهٔ دریافت، فاصلهٔ هر جفت، ساعت تهران (شامل بازهٔ عبوری از نیمه‌شب)، تعداد/مهلت دعوت، اعتبار کد و پیش‌نمایش، هزینهٔ روزانه/هر تماس و سقف بازنویسی را نگه می‌دارد. برای سقف‌های تعداد/فاصله/مهلت دعوت،۰یعنی غیرفعال؛ برای ساعت، تیک «ارسال فقط در ساعت مجاز» را بردارید. برای برداشتن سقف کل GapGPT، گزینهٔ «بدون سقف روزانهٔ کل بازنویسی GapGPT» را فعال کنید؛ سقف هر حساب باقی می‌ماند. با خاموش‌بودن گزینه، عدد سقف کل اعمال می‌شود و۰یعنی بازنویسی غیرفعال؛ کلید و مدل خالی از ادمین فعال نمی‌شوند. قابلیت نامحدود به مهاجرت۰۰۲۸نیاز دارد؛ پیش‌فرض آن خاموش است و مصرف قبلی را تغییر نمی‌دهد.

در «کنترل تعداد درخواست‌ها»، هر ردیف نوع درخواست، تعداد، بازهٔ ثانیه‌ای و تیک فعال دارد؛ OTP، آماده‌سازی، سفارش، دعوت و لینک خصوصی ردیف جدا دارند. کنترل حدس OTP و لینک خصوصی و callback باید مثبت و فعال بمانند؛ تعداد و بازهٔ آن‌ها قابل تنظیم است. تأیید شماره، CSRF، قطع دریافت، کنترل محتوا، ممنوعیت دعوت خود/عضو قبلی/دعوت چندنفره، یکتایی سفارش و رسید نامعلوم قابل دورزدن نیستند. سقف فنی طول SMS، عمر قابلیت‌های خصوصی و انقضای سفارش/تطبیق نتیجهٔ نامعلوم، تنظیم تجاری تعداد و ساعت نیستند و حفظ شده‌اند.

اصلاح تازهٔ محلی: صفر در «بازهٔ شمارش ارسال/دریافت/دعوت (ساعت)» نیز سقف تعداد همان بازه را غیرفعال می‌کند، حتی اگر عدد تعداد مثبت باشد. تعداد تنظیم‌شده و سابقهٔ مصرف پاک نمی‌شوند؛ با مثبت‌کردن بازه، مصرف موجود دوباره محاسبه می‌شود. صفر در فاصله‌های دریافت، جفت فرستنده/گیرنده و دعوت یعنی بدون فاصلهٔ اجباری. در ساعت شروع و پایان روز، صفر معنی نیمه‌شب دارد: مثلاً ۲۲ تا ۰ مجاز است. برای حذف کامل برنامهٔ ساعت، تیک «ارسال فقط در ساعت مجاز» را بردارید؛ در حالت خاموش، شروع و پایان ۰ هم قابل ذخیره‌اند. اعتبار OTP/پیش‌نمایش و تعداد تلاش ورود همچنان باید مثبت بمانند. مهاجرت ۰۰۲۹ فقط راهنمای فیلدها را ثبت می‌کند و هیچ مقدار ذخیره‌شده‌ای را عوض نمی‌کند. این اصلاح هنوز روی سرور منتشر نشده است.

مجوز مستقل `core.manage_site_limits` لازم است. هر ذخیره دلیل و سابقهٔ قبل/بعد دارد؛ ذخیرهٔ فرم قدیمی با revision ناهماهنگ رد می‌شود. تغییر سیاست بدون restart اعمال می‌شود و فقط رویدادهای ارسال‌نشده‌ای که بابت ساعت/فاصله منتظر بوده‌اند، برای بررسی دوباره آماده می‌شوند. پذیرفته‌شده، نتیجهٔ نامعلوم و لغوشده دوباره ارسال نمی‌شوند. بودجه/مصرف/هدیه بازنشانی نمی‌شود؛ سقف هزینهٔ غیرعادی هر تماس واقعی باید مثبت بماند و حالت هزینهٔ نامحدود فقط با مجوز env قبلی مجاز است.

مسیر ادمین در Django و پراکسی Next، `Referrer-Policy: same-origin` دارد تا فرم‌های POST مرورگر مبدأ معتبر برای CSRF بفرستند؛ سیاست `no-referrer` روی فرم عادی می‌توانست `Origin: null` و خطای ورود ایجاد کند. API و لینک خصوصی همچنان `no-referrer` هستند؛ مبدأ null به فهرست اعتماد اضافه نشده و توکن CSRF لازم است. [توضیح رسمی Django دربارهٔ حذف Referer](https://docs.djangoproject.com/en/5.2/ref/csrf/#removing-the-referer-header) مرجع این اصلاح است.

ابتدا migration0016 و سپس `python manage.py configure_limits --reason 'Initialize runtime policy'` را با محیط صحیح اجرا کنید تا تمام ردیف‌های ادمین از تنظیم محیط ساخته شوند. در نبود ردیف ذخیره‌شده، رفتار قبلی از env برقرار است. `--relax-business` فقط در پروفایل هدیه با پرداخت بسته، محدودیت‌های تجاری تعداد/زمان و کنترل‌های درخواست غیرامنیتی را خاموش می‌کند؛۳هدیه را تغییر نمی‌دهد. این عملیات باید برای هر محیط جداگانه و با مجوز همان محیط اجرا شود.

طبق درخواست این نوبت، فقط روی لوکال از `python3 scripts/dev-product.py --relax-business-limits` استفاده شد؛ اجرای عادی `make dev-product` انتخاب بعدی مدیر را حفظ می‌کند و دوباره محدودیت‌ها را خاموش نمی‌کند. برای ساخت مدیر لوکال توسط خود کاربر: `python3 scripts/dev-product.py --manage createsuperuser`؛ رمز را در همان ترمینال وارد کنید. این فرمان از محیط خصوصی و دیتابیس مستقل لوکال استفاده می‌کند. migration جدید سقف ثابت۳نوبت را از قید دیتابیس دعوت حذف می‌کند؛ اگر تاریخچه نوبت چهارم یا بیشتر ایجاد شود، بازگردانی schema قدیمی ممکن است رد شود و نباید برای rollback تاریخچه حذف شود.

بررسی فنی بر اساس [مستندات رسمی ادمین Django5.2](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/) و [قیود مدل](https://docs.djangoproject.com/en/5.2/ref/models/constraints/) انجام شد؛ Context7 در این نشست در دسترس نبود. [برآورد ظرفیت با منابع اعلام‌شدهٔ فعلی](capacity-current.fa.md) جداگانه ثبت شده است.

## اجرای محصول واقعی روی همین کامپیوتر

برای تست تعاملی کارفرما، `make dev-product` بک‌اند، worker و beat بومی را همراه `next dev` با Fast Refresh اجرا می‌کند. آدرس `https://localhost:3000` است؛ OTP و پیامک با اعتبارنامهٔ خصوصی کاوه‌نگار واقعی‌اند، سه هدیه و جایزهٔ دعوت حفظ می‌شوند و پرداخت پولی بسته است. این فرمان هیچ کاری روی سرور اصلی انجام نمی‌دهد و ارسال نمونه یا حساب ساختگی ایجاد نمی‌کند. فرانت فقط مسیر API و گواهی عمومی محلی را می‌گیرد؛ کلیدهای provider، پایگاه داده و رمزنگاری به محیط فرانت منتقل نمی‌شوند.

پیش‌نیاز: محیط `backend/.venv`، وابستگی‌های نصب‌شدهٔ فرانت، `openssl` و سرویس‌های دادهٔ محلیِ در حال اجرا روی PostgreSQL:15439، Redis:16389 و RabbitMQ:15679. کلیدها و مشخصات اتصال از `.env` خصوصی خوانده می‌شوند. دیتابیس مستقل `begamnagam_local_product`، Redis DB8 با پیشوند مخصوص و صف `begamnagam-local-real` مانع پردازش سفارش‌های demo قدیمی یا تغییر دادهٔ محصول اصلی می‌شوند. حالت نامعلوم/آزمایشی موجود رد می‌شود؛ توقف ایمنی موجود خودکار باز نمی‌شود. سقف روزانهٔ سراسری طبق مجوز کارفرما نامحدود و سقف غیرعادی هر تماس و کنترل‌های محتوا/دریافت برقرار است.

هر دو listener فقط روی `127.0.0.1` و با TLS اجرا می‌شوند. Secure cookie و CSRF باقی‌اند؛ بک‌اند به هدرهای scheme اعتماد نمی‌کند و فرانت گواهی همان بک‌اند محلی را با CA صریح بررسی می‌کند. گواهی۱۴روزهٔ localhost و کلید خصوصی0600 در `.local/local-product/` ساخته می‌شوند؛ اعتماد سیستم تغییر نمی‌کند. هشدار اولین بازدید باید توسط خود کاربر تأیید شود. لاگ‌ها خصوصی‌اند و سرور WSGI محلی access log شامل URL ثبت نمی‌کند. با Ctrl-C هر چهار پردازش بسته می‌شوند؛ داده حفظ می‌شود. پورت‌های3000/8000 باید پیش از شروع آزاد باشند؛ ابزار هیچ پردازش نامربوطی را متوقف نمی‌کند.

داده و حساب‌های این محیط از محصول اصلی مستقل‌اند. لینک دریافت/لغو در پیامک به localhost اشاره می‌کند و فقط روی همین کامپیوتر قابل بازشدن است؛ مجوز لینک دامنهٔ اصلی، پذیرش لینک localhost در کاوه‌نگار را تضمین نمی‌کند. برای بررسی گوشی خارج از این کامپیوتر از انتشار مجاز با دامنهٔ قابل‌دسترسی استفاده شود. این محدودیت با تحویل ساختگی پنهان نمی‌شود.

Context7 در نشست پیاده‌سازی در دسترس نبود؛ راهنمای همراه Next و [مرجع رسمی HTTPS در next dev](https://nextjs.org/docs/app/api-reference/cli/next#using-https-during-development) و [تنظیمات امنیتی Django](https://docs.djangoproject.com/en/5.2/ref/settings/#secure-proxy-ssl-header) بررسی شدند.

### بازیابی خطای ۵۰۳ در محصول واقعی لوکال

اگر فرانت و API روشن‌اند ولی `/healthz` یا `/api/v1/bootstrap` پاسخ۵۰۳می‌دهند،
ابتدا Docker Desktop و سرویس‌های داده را بررسی کنید. در رخداد ۲۰۲۶-۱۰-۲۹،
Docker خاموش بود و هیچ listener روی پورت‌های۱۵۴۳۹،۱۶۳۸۹و۱۵۶۷۹وجود نداشت.
برای بازیابی **محیط موجود همین دستگاه** با فایل override محلی موجود:

```sh
docker desktop start --timeout 60
docker compose -f compose.yaml -f .local/compose.validation.yaml \
  start --wait --wait-timeout 60 postgres redis rabbitmq
```

فرمان `start` کانتینرهای موجود را شروع می‌کند. برای این بازیابی، فرانت بومی
Fast Refresh روشن می‌ماند؛ اجرای کل demo، build، حذف volume یا ساخت دیتابیس
جایگزین لازم نیست. این فرمان راه‌اندازی نخستین دستگاه تازه نیست؛ در نبود فایل
override یا کانتینرهای قبلی، ابتدا پیکربندی موجود و محل داده را مشخص کنید.

در این بازیابی، هر سه سرویس healthy شدند؛ `/healthz`، bootstrap مستقیم API و
bootstrap از فرانت با TLS و CA محلی پاسخ۲۰۰دادند. `demo_mode:false` و
`otp_is_real:true` تأیید شدند؛ استعلام فقط‌خواندنی کاوه‌نگار موفق و اعتبار OTP
کافی بود. فرم واقعی ورود در مرورگر، بدون mock، فعال و بدون خطای JavaScript بود.
پیامک برای این بررسی درخواست نشد؛ کاربر از `https://localhost:3000/profile`
کد واقعی را درخواست می‌کند. کلیدها، داده، تنظیم پرداخت و محدودیت‌ها حفظ شدند.

مراجع: [راه‌اندازی Docker Desktop](https://docs.docker.com/reference/cli/docker/desktop/start/)
و [شروع کانتینرهای موجود Compose](https://docs.docker.com/reference/cli/docker/compose/start/).

## پروفایل کاربر

دکمهٔ «پروفایل» در صفحهٔ اول به `/profile` می‌رود. کاربر با OTP وارد می‌شود و شمارهٔ پوشیدهٔ تأییدشده، ماندهٔ ارسال و پاداش دعوت را از bootstrap می‌بیند؛ سابقه، دعوت و تنظیم دریافت در دسترس‌اند. خروج با POST محافظت‌شده با CSRF، نشست و اطلاعات رابط را پاک می‌کند و کاربر به خانه برمی‌گردد. این صفحه noindex/no-store است و شمارهٔ کامل یا دادهٔ حساب در HTML اولیه قرار نمی‌گیرد.

## ارسال واقعی هدیه از نسخه۰٫۸٫۱۵

کارفرما برای `begamnagam.ir`، OTP واقعی و ۳ هدیهٔ واقعی برای هر حساب را مجاز کرده و پرداخت پولی را بسته نگه داشته است. پروفایل `config.live_sms_settings` از همان اعتبارسنجی proxy/TLS داخلی استفاده می‌کند؛ `compose.internal.yaml` انتخاب پروفایل و DEMO_MODE را از env خصوصی می‌گیرد و در نبود آن‌ها همچنان demo است. متغیرهای فعال: `DEMO_MODE=0`, `SMS_BACKEND=kavenegar`, `OTP_BACKEND=kavenegar`, `PAYMENT_BACKEND=disabled`, `PROVIDER_NETWORK_MODE=external`, `LIVE_PROVIDERS_ENABLED=1`, `PROVIDER_ENVIRONMENT=live`, `LOCAL_REAL_OTP_ENABLED=0`, `DEMO_TEST_TOOLS_ENABLED=0`, `SMS_RECIPIENT_POLICY=all`. کلید و فرستندهٔ کاوه‌نگار و نسخهٔ جاری شرایط لازم‌اند. فعال‌سازی پرداخت همچنان به اعتبارنامه و تأییدهای مخصوص خودش نیاز دارد؛ این پروفایل هیچ تأیید قراردادی یا حقوقی را جعل نمی‌کند.

از نسخه۰٫۱۰٫۱، طبق دستور صریح کارفرما، `PROVIDER_DAILY_BUDGET_UNLIMITED=1` سقف هزینهٔ روزانهٔ سراسری را در همین پروفایل هدیهٔ واقعی برمی‌دارد. دفتر ثبت هزینه و مقدار تاریخی۱۰۰٬۰۰۰ریال پاک یا بازنشانی نمی‌شوند؛ آن مقدار در این حالت مانع ارسال نیست. OTP، پیام و دعوت همچنان در دفتر مشترک ثبت می‌شوند. پیش‌فرض متغیر۰است؛ در demo، تست محلی OTP و پرداخت پولی، فعال‌کردنش در startup رد می‌شود. `PROVIDER_DAILY_BUDGET_RIAL=0` به‌تنهایی به معنی نامحدود نیست.

بررسی هزینهٔ غیرمنتظرهٔ هر تماس حفظ شده است: OTP۱۰٬۰۰۰ریال و پیام/دعوت۲۰٬۰۰۰ریال رزرو می‌کنند؛ هزینهٔ اعلامی بیشتر، هشدار و توقف خودکار می‌سازد. این اعداد تعرفهٔ تضمینی نیستند. رسید `accepted` خوانده‌شدن نیست؛ نتیجهٔ نامعلوم بدون ارسال دوباره تطبیق داده می‌شود. سه هدیهٔ اولیه، پاداش دعوت، محدودیت‌های مقابله با سوءاستفاده و پرداخت بسته تغییری نمی‌کنند.

در snapshot عملیات، `provider_budget_unlimited:true` و `provider_budget_limit_rial:null` نشان‌دهندهٔ این حالت‌اند؛ ماندهٔ رزرو همچنان عدد واقعی دفتر است و هشدار۸۰درصد روزانه غیرفعال می‌شود. برای بازگشت به حالت محدود، flag را۰کنید؛ حد مؤثر دوباره کمینهٔ سقف env و ردیف همان روز است. هزینه‌های قبلی آزاد نمی‌شوند. تغییر env خصوصی به بازسازی یک‌بارهٔ backend/worker/beat نیاز دارد؛ frontend و سرویس‌های داده تغییری ندارند. Context7 در این نشست ابزار قابل‌فراخوانی نداشت؛ [مرجع رسمی تنظیمات Django](https://docs.djangoproject.com/en/5.2/topics/settings/) و [تقدم env در Compose](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/) بررسی شدند.

قبل از تغییر حالت، ارسال را متوقف و نبودن صف حل‌نشده را بررسی کنید. فرمان `python manage.py launch_live_gifts` فقط در حالت واقعیِ هدیه و توقف ارسال اجرا می‌شود؛ یک‌بار ماندهٔ حساب‌هایی را که ارسال واقعی نداشته‌اند به۳برمی‌گرداند و سابقه ثبت می‌کند. پیام‌های قبلی بازپخش نمی‌شوند، سهمیهٔ واقعی دوباره شارژ نمی‌شود و بودجه پاک یا افزایش نمی‌یابد. پیش‌نمایش و تأیید شرایط باید مربوط به نسخهٔ جاری باشند.

در آزمون اول۰٫۸٫۱۵، کاوه‌نگار خطای۴۲۰(مجوز لینک) داد. پس از فعال‌شدن مجوز توسط کارفرما، آزمون تازه با رسید واقعی `delivered` موفق و `provider_link_permission` با سابقه بسته شد؛ ارسال نهایی اکنون باز است. لینک قطع دریافت را حذف یا برای عبور از فیلتر مبهم نکنید. در رخداد مجدد این خطا، مجوز دامنه را بررسی، alert را با سابقه ببندید و SafetyControl را از پنل نقش مجاز resume کنید؛ آزمون قطعیِ ردشده مجوز ارسال مجدد خودکار ندارد. تکرار درخواست نامعلوم فقط با استعلام وضعیت تطبیق داده می‌شود. `scripts/verify-domain-routing.py --expect-live-gifts` مسیر واقعی و بسته‌بودن پرداخت را بدون پیامک یا تراکنش بررسی می‌کند.

`debugmode=disabled` در خواندن مستقل حساب تأیید شد. برای `resendfailed`، درخواست خاموش‌کردن با POST و GET پاسخ `disabled` داد اما خواندن مستقل همچنان `enabled` گزارش می‌کند؛ موفقیت پاسخ تغییر، اثبات ماندگاری آن نیست. هشدار `provider_resend_setting` با شدت warning برای بررسی از پنل ثبت شده و باید پس از تأیید خاموش‌شدن آن بسته شود. صف برنامه همچنان هر سفارش را یک‌بار submit می‌کند و هزینهٔ آغازشده از برنامه را رزرو می‌کند؛ رفتار ارسال مجدد داخلی provider باید جداگانه در پنل کنترل شود.

این راهنما برای demo محلی است. Compose عمداً `DEBUG=0` و `DEMO_MODE=1` را ثابت نگه می‌دارد؛ صرف تغییر `.env` آن را به سرویس واقعی تبدیل نمی‌کند. کلیدهای برنامه، رمز PostgreSQL و رمز RabbitMQ باید از env خصوصی تأمین شوند و مقدار جایگزین ثابت ندارند. پورت‌ها روی `127.0.0.1` هستند و نباید بدون تکمیل فاز انتشار به اینترنت باز شوند.

## گردش‌کار روزمره UI

منوی متحرک مشترک موبایل/دسکتاپ و قاب برجسته در `dev` آماده است؛ ترتیب
برآمدگی، قطره و پرشدن آیکن، رنگ‌های تم و کاهش حرکت در
[راهنمای منو](navigation.fa.md) مستند شده‌اند. این تغییر به راه‌اندازی دوبارهٔ
سرویس‌ها، مهاجرت یا تغییر تنظیمات provider نیاز ندارد.

تغییر تم از دکمهٔ ماه/خورشید کنار پروفایل انجام می‌شود و روی همین دستگاه
حفظ می‌شود. [راهنمای تم](theme.fa.md) رفتار سیستم، تب‌ها، کاهش حرکت و
آزمون‌های مرورگر را توضیح می‌دهد؛ این قابلیت به API یا تنظیم جدید محیط نیاز ندارد.

تست تعاملی کارفرما از محصول باید روی پروفایل واقعی و همان حساب‌ها/سابقهٔ محصول انجام شود؛ OTP، پیام گیرنده و دعوت همگی واقعی‌اند. اجرای demo، console یا پایگاه SQLite پیش‌نمایش فقط با درخواست صریح شبیه‌سازی مجاز است. خرابی محصول، مجوز جایگزینی آن با موفقیت ساختگی نیست. نمونه‌های توسعه و آزمون خودکارِ جدا برای کار فنی‌اند و نباید به‌عنوان محصول در مرورگر کارفرما نمایش داده شوند. تغییر کد و استقرار تازه فقط با دستور صریحِ ارسال روی سرور انجام می‌شود.

با backend فعال روی localhost:8000، از ریشه `make dev-ui` را اجرا کنید. این فرمان فقط `npm run dev` است و Next.js Fast Refresh را فعال می‌کند؛ ذخیرهٔ فایل تغییر را در مرورگر اعمال می‌کند. `npm ci` فقط در نصب اول یا تغییر lockfile لازم است.

اگر frontend کانتینری پورت۳۰۰۰ را گرفته است، `docker compose stop frontend` بزنید و بقیه سرویس‌ها را روشن نگه دارید. اگر frontend نیتیو در حالت `next start` اجرا می‌شود، همان پردازش را یک بار متوقف و با `make dev-ui` جایگزین کنید. هنگام ویرایش‌های بعدی سرور را restart نکنید و image نسازید. تغییر متغیرهای محیط/پیکربندی ممکن است restart یک‌باره بخواهد.

SW فقط در production ثبت می‌شود؛ سناریوهای نصب و آفلاین را در بررسی انتشار جدا اجرا کنید. این کار نیازی به ساخت image در هر ویرایش UI ایجاد نمی‌کند. [راهنمای رسمی Fast Refresh](https://nextjs.org/docs/architecture/fast-refresh) و [فرمان next dev](https://nextjs.org/docs/app/api-reference/cli/next) مبنای این گردش‌کارند.

در نسخه۰٫۳٫۲، رفت‌وبرگشت یک متغیر CSS آزمایشی در مرورگر با ثابت‌ماندن `performance.timeOrigin` تأیید شد؛ صفحه reload و image ساخته نشد. تغییر آزمایشی برگشت داده شد. ۱۰ تست فرانت و typecheck نیز موفق بودند. فایل تولیدی `next-env.d.ts` از Git خارج شده و `npm run typecheck` ابتدا `next typegen` را بدون build تولیدی اجرا می‌کند.

## شروع کامل demo

از ریشهٔ مخزن:

```sh
python3 scripts/init-local.py
docker compose config --quiet
docker compose up --build -d --wait --wait-timeout 300
python3 scripts/smoke.py
```

نصب اول به دریافت image و dependency نیاز دارد؛ دانلود پیش از زمان انتظار سلامت انجام می‌شود. `--wait` سلامت سرویس‌ها را پس از بالا آمدن بررسی می‌کند. migration در سرویس یک‌باره انجام می‌شود و backend پس از موفقیت آن شروع می‌شود. worker و beat پس از سلامت backend فعال می‌شوند. در هر محیط فقط یک beat برای این پروژه اجرا کنید.

```sh
docker compose ps
docker compose logs --tail=100 backend worker beat frontend
```

`make up`، `make logs`، `make smoke` و `make down` میان‌بر همین کارها هستند. `.env` فقط یک بار ساخته می‌شود؛ کلیدهای آن و volumeهای پایگاه داده را با هم نگه دارید. تغییر کلید رمزنگاری بدون مهاجرت، شماره‌های قدیمی را ناخوانا می‌کند؛ تغییر کلید HMAC تطبیق شماره و توقف دریافت را می‌شکند.

## محیط سبک بدون Docker

برای توسعهٔ سریع، بک‌اند بدون `DATABASE_URL` از SQLite، بدون `REDIS_URL` از حافظهٔ همان فرایند و بدون broker از اجرای eager استفاده می‌کند. این حالت برای توسعه و تست واحد است و رفتار قفل‌ها و صف واقعی را اثبات نمی‌کند.

```sh
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.lock.txt
cd backend
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

در ترمینال دیگری، از ریشه:

```sh
cd frontend
npm ci
npm run dev
```

سپس رابط روی `http://localhost:3000` است. `frontend/.env.example` تنظیم `INTERNAL_API_URL` و متغیرهای SEO را توضیح می‌دهد. برای اجرای نیتیو، نمونه را به `frontend/.env.local` کپی کنید یا متغیرهای لازم را در محیط همان پردازش export کنید؛ `make dev-ui` فایل `.env` ریشهٔ Compose را خودکار وارد محیط Next نمی‌کند. در dev پس از تغییر تنظیم محیط، dev server را یک بار restart کنید. در خروجی standalone، rewrite و خروجی SEO هنگام build ثبت می‌شوند؛ بعد از تغییر مقصد API، `APP_BASE_URL` یا `SEO_INDEXABLE` دوباره frontend را build کنید. برای تست PostgreSQL و RabbitMQ از Compose استفاده کنید.

## تنظیم SEO و انتشار

`APP_BASE_URL` مبدأ یکتای canonical، Open Graph، JSON-LD و sitemap فرانت و نشانی لینک‌های گیرنده در بک‌اند است؛ این دو بخش باید یک مبدأ هماهنگ داشته باشند. `SEO_INDEXABLE=0` پیش‌فرض است: demo محلی، CT خصوصی و staging باید `noindex` بمانند و sitemap خالی باشد. robots خواندن HTML را مجاز می‌گذارد تا crawler بتواند `noindex` را ببیند؛ مسیرهای API/admin منع می‌شوند. فقط پس از مجوز انتشار عمومی، با دامنهٔ واقعی HTTPS، مقدار۱ مجاز است؛ این متغیر هیچ provider یا استقراری را فعال نمی‌کند.

Compose توسعه هر دو مقدار را هنگام ساخت image فرانت می‌فرستد. در Compose داخلی/انتشار که image آماده می‌گیرد، باید همان image با build argهای درست ساخته شده باشد؛ تغییر `.env.internal` / `.env.release` در زمان اجرا، metadata، robots و sitemap آماده را اصلاح نمی‌کند. برای دستور ساخت و بررسی مسیرهای عمومی/خصوصی، [راهنمای SEO](seo.md) را دنبال کنید. این بررسی انتشار جدا از حلقهٔ روزمرهٔ Hot Reload است.

## هاردنینگ و بررسی خواندنی امنیت

**وضعیت ظرفیت۲۸اکتبر:** پس از رفع وضعیت emergency_ro توسط کارفرما، [پیکربندی۰٫۱۱٫۲](release-v0.11.2-capacity/README.fa.md) و اصلاح keepalive روی Nginx مرکزی فعال و [آزمون۳۰دقیقه‌ای مسیر دامنه](performance-2026-10-28/optimized.fa.md) کامل شد. انتشار بعدی[۰٫۱۲٫۰با GapGPT](deployments/ct115-0.12.0-gapgpt.json) همین ظرفیت را حفظ کرد؛ مسیر جاری `/opt/begamnagam/releases/0.12.0-gapgpt` است. در recreate جاری، هر سه فایل `compose.internal.yaml`، `compose.hardened.yaml` و `compose.performance.yaml` لازم‌اند؛ image تمام شش فرانت یکسان باشد. فایل Ollama در پیکربندی فعال نیست.

[نتیجهٔ آزمون دود/بار/فشار۲۸اکتبر](performance-2026-10-28/README.fa.md) روی CT زنده، مرجع ظرفیت خواندنِ اندازه‌گیری‌شدهٔ۰٫۱۱٫۰است. ابزار `scripts/live-read-load.py` فقط مسیرهای GET مشخص را می‌فرستد؛ نشست‌های بی‌نامِ خودش را پاک می‌کند و OTP/پیام/پرداخت/AI را فراخوانی نمی‌کند. `scripts/smoke.py` قدیمی همچنان فقط demo است؛ guard آن را روی production خاموش نکنید. تست زنده نیازمند مجوز اپراتور، پایش، آستانهٔ توقف و حفظ TLS معتبر است. گزارش، روش loopback، HTTPS مستقیم CT و HTTPS دامنه از edge را جدا می‌کند؛ نتایج مستقیم برنامه به‌تنهایی ظرفیت عمومی سایت نیستند.

[گزارش امنیت ۲۰۲۶-۱۰-۲۷](security-audit-2026-10-27.fa.md) بررسی اولیه را ثبت می‌کند. اصلاحات با مجوز کارفرما در[نسخهٔ۰٫۱۱٫۰](release-v0.11.0/README.fa.md) روی CT فعال و آزموده شدند؛ گزارش انتشار، شواهد، موارد باز و ترتیب rollback مرجع جاری‌اند. اجرای `python manage.py audit_security --database --redis` در backend فقط metadata نقش/اتصال و PING بدون رمز را بررسی می‌کند و secret چاپ نمی‌کند؛ خروجی محلی شاهد سرور نیست.

در CT جاری، **همیشه** `compose.internal.yaml` و `compose.hardened.yaml` را با هم به Compose بدهید؛ این موضوع در recreate/انتشار بعدی هم لازم است. `APPLICATION_ENV_FILE` فقط credential اجرای برنامه، `MIGRATION_ENV_FILE` credential مالک schema و `SERVICE_SECURITY_DIR` فایل‌های خصوصی ACL/سلامت Redis را تعیین می‌کنند. فایل کامل `.env.internal` برای interpolation مدیریت است و نباید env برنامه/فرانت شود. تغییر schema با سرویس `migrate` انجام می‌شود؛ نقش runtime اجازهٔ DDL ندارد.

ورود SSH فقط با کلید موجود برقرار است؛ رمز و forwarding بسته‌اند. فایروال ماندگار، SSH/TLS شبکهٔ خصوصی و HTTP فقط از edge را می‌پذیرد. PostgreSQL و RabbitMQ همچنان روی کانتینر/volume قبلی‌اند؛ Redis با ACL جدید و همان volume اجرا می‌شود. `systemctl list-timers 'begamnagam-*'` وضعیت بکاپ روزانه و آزمون هفتگی restore را نشان می‌دهد. کلید backup مستقل0600 خارج release است؛ archive و کلید جداگانه روی دستگاه اپراتور نیز کپی شدند. replication خودکار خارج میزبان و سیاست نگهداری هنوز تنظیم نشده‌اند.

محدودکنندهٔ ورود ادمین مستقل از محدودیت‌های محصول است:۱۰تلاش هر IP/نام و۵۰تلاش هر IP در۶۰۰ثانیه، با خطای۴۲۹/`Retry-After`؛ خرابی Redis ورود تازه را می‌بندد. CSP بک‌اند scriptهای خود سایت را مجاز می‌کند؛ صفحات فرانت nonce مستقل و رندر پویا دارند. `celery inspect` پس از انتشارِ remote control خاموش، ابزار سلامت این پروفایل نیست؛ سلامت فرایند، سن outbox و وضعیت واقعی broker بررسی شوند.

serializer جدید Redis، JSON و شمارندهٔ اتمیک integer را نگه می‌دارد؛ Redis واقعی را خالی نکنید. migration0017 بدنهٔ قالب‌های انتخاب‌شده را نیز رمز می‌کند؛ اجرای آن باید با کلیدهای موجود، بکاپ و امکان rollback باشد. `rotate_encryption` فیلدهای جدید را هم پوشش می‌دهد و HMAC تطبیق شماره را تغییر نمی‌دهد. برای تعیین ACL، schema owner مستقل و کاربر محدود broker، برنامهٔ اقدام گزارش را دنبال کنید؛ صرف تغییر کد، مجوزهای سرویس‌های فعال را اصلاح نمی‌کند.

`DATABASE_URL` اکنون گزینه‌های `sslmode`، `sslrootcert`، `sslcert`، `sslkey`، `connect_timeout` و `application_name` را به libpq منتقل می‌کند؛ گزینهٔ ناشناخته، خالی یا تکراری رد می‌شود. timeout پیش‌فرض۵ثانیه و محدودهٔ مجاز۱تا۳۰ثانیه است. برای DB روی شبکهٔ نامطمئن، `sslmode=verify-full` و CA معتبر لازم است؛ گذرواژه یا DSN را در لاگ یا آرگومان فرمان عمومی چاپ نکنید. سه کلید application باید مستقل باشند و در non-demo کلیدهای یکسان/مشتق‌شدهٔ ناامن رد می‌شوند.

| `CELERY_BROKER_URL` | RabbitMQ؛ اطلاعات حساس در payload صف قرار نمی‌گیرد |
| `CELERY_TASK_ALWAYS_EAGER` | اجرای هم‌زمان مخصوص تست سبک؛ Compose برابر صفر است |
| `PRICE_TOMAN` | مبلغ صحیح آزمایشی؛ Compose برابر ۲۰۰۰ |
| `SENDER_DAILY_LIMIT` | سقف سفارش فرستنده در ۲۴ ساعت گذشته؛ پیش‌فرض ۵ |
| `RECIPIENT_COOLDOWN_HOURS` | فاصلهٔ سراسری گیرنده؛ پیش‌فرض ۲۴ ساعت |
| `SENDER_RECIPIENT_COOLDOWN_HOURS` | فاصلهٔ همان فرستنده به همان گیرنده؛ پیش‌فرض ۲۴ ساعت |
| `DEMO_TEST_TOOLS_ENABLED` | پیش‌فرض۰؛ ابزار ادمین برای ریست شمارش و فعال‌سازی ارسال نامحدودِ یک حساب، فقط در demo |
| `AI_MODE` | `template`، `ollama` برای انتخاب قالب، یا `gapgpt` برای بازنویسی بررسی‌شده |
| `OLLAMA_URL`, `OLLAMA_MODEL` | مقصد و نام مدل محلی، فقط برای حالت اختیاری |
| `APP_BASE_URL` | مبدأ لینک تنظیمات گیرنده و URLهای SEO فرانت؛ پیش‌فرض محلی، در فرانت هنگام build ثبت می‌شود |
| `SEO_INDEXABLE` | پیش‌فرض۰؛ فقط انتشار عمومیِ مجاز با HTTPS واقعی می‌تواند۱ باشد؛ تغییر آن به build دوبارهٔ فرانت نیاز دارد |
| `KAVENEGAR_API_KEY` | کلید خصوصی پنل کاوه‌نگار؛ در `.env` ریشه، فقط سمت سرور |
| `KAVENEGAR_SENDER` | شماره خط ارسال تأییدشدهٔ کاوه‌نگار |
| `KAVENEGAR_OTP_MODE` | پیش‌فرض `sms`: ارسال عادی کد؛ `lookup`: استفاده از الگوی تأییدشده |
| `KAVENEGAR_OTP_TEMPLATE` | فقط در حالت `lookup` لازم است؛ در حالت فعلی `sms` خالی می‌ماند |
| `LOCAL_REAL_OTP_ENABLED` | پیش‌فرض۰؛ فعال‌سازی مستقل OTP واقعی برای ورود همهٔ شماره‌های معتبر، با سقف هزینه و درخواست |
| `INTERNAL_DEMO_HOST` | فقط پروفایل CT: IP خصوصی صریح روی HTTPS؛ بودجه و محدودیت OTP حفظ می‌شوند |
| `PROVIDER_DAILY_BUDGET_RIAL` | سقف رزرو ناخالص روزانه به ریال؛ موفقیت یا پاسخ نامعلوم رزرو را آزاد نمی‌کند |
| `OTP_MAX_COST_RIAL` | سقف رزرو هر درخواست OTP به ریال؛ باید مثبت و در بودجه روزانه باشد |
| `DOCKER_SUBNET` | شبکهٔ اختصاصی Compose؛ پیش‌فرض `10.253.241.0/24`، قابل تغییر در صورت تداخل |

نمونه‌های URL و رمز در `.env.example` مخصوص محلی‌اند. Compose متغیرهای کاوه‌نگار بالا را از `.env` به backend، migrate، worker و beat منتقل می‌کند؛ فرانت به آن‌ها دسترسی ندارد. اعتبارنامه‌ها پیش‌فرض خالی‌اند و افزودن کلید، حالت demo یا شبکهٔ خاموش را تغییر نمی‌دهد. در اجرای مستقیم Django، باید متغیرها را به محیط پردازش وارد کنید؛ فایل `.env` خودکار بارگذاری نمی‌شود. کلید را در URL مرورگر، لاگ، مخزن یا متغیر `NEXT_PUBLIC_*` قرار ندهید.

از نسخه۰٫۸٫۲، مسیر OTP کاوه‌نگار پیش‌فرض `sms/send` است. در dev/لوکال، متن ثابت فقط شامل نام سرویس و خط `Code:` با کد چهاررقمی است؛ زیرعنوان و تاریخ/ساعت حذف شده‌اند؛ ورودی آزاد کاربر وارد آن نمی‌شود. شمارهٔ خط از `KAVENEGAR_SENDER` گرفته می‌شود و `hide=1` ارسال می‌شود. در پاسخ نامعلوم، ارسال خودکار تکرار نمی‌شود و کد در API یا لاگ نمایش داده نمی‌شود. پس از تأیید الگو می‌توان `KAVENEGAR_OTP_MODE=lookup` و `KAVENEGAR_OTP_TEMPLATE` را تنظیم کرد؛ الگوی خالی در حالت lookup رد می‌شود. ارسال عادی تابع محدودیت خط و شماره‌های مسدود اپراتور است؛ تحویل به همهٔ شماره‌ها تضمین نمی‌شود.

تنظیم‌های غیرآزمایشی ناقص، در startup رد می‌شوند؛ کلاینت provider پیاده و با HTTP fixture آزموده شده است؛ پذیرش خارجی و فعال‌سازی همچنان باز است. برای تنظیمات جداگانه انتشار از `deploy/release.env.example` و برای پیش‌نیازهای فعال‌سازی و rollback از [runbook۰٫۷](release-v0.7/RUNBOOK.fa.md) استفاده کنید. مشخصات API مرجع در [مستندات رسمی کاوه‌نگار](https://kavenegar.com/rest.html) آمده است.

### تست محلی OTP واقعی، با پرداخت و پیام آزمایشی

نسخه۰٫۸٫۳ مسیر مستقلی برای کد ورود واقعی اضافه کرد؛ به درخواست کارفرما، از نسخه۰٫۸٫۱۴ فهرست مجاز شماره‌های ورود حذف شده است. در `.env` خصوصی، `OTP_BACKEND=kavenegar` و `LOCAL_REAL_OTP_ENABLED=1`، کلید/خط واقعی، `KAVENEGAR_OTP_MODE=sms` و بودجه‌های مثبت لازم‌اند. همهٔ شماره‌های معتبر ایران می‌توانند کد بگیرند؛ `OTP_TEST_RECIPIENT_HASHES` دیگر خوانده نمی‌شود و باید از env جاری حذف شود. شمارهٔ خام و کد را در فایل یا لاگ نگه ندارید.

برای این حالت، `DEMO_MODE=1`، `SMS_BACKEND=console`، `PAYMENT_BACKEND=demo`، `PROVIDER_NETWORK_MODE=disabled` و `LIVE_PROVIDERS_ENABLED=0` اجباری‌اند. مبدأ برنامه باید loopback یا مبدأ HTTPS صریحِ پروفایل داخلی/دامنه باشد. فقط متد OTP به مقصد ثابت `https://api.kavenegar.com` اجازه دارد؛ متد عمومی ارسال، استعلام SMS و زرین‌پال همچنان بسته‌اند. redirect دنبال نمی‌شود. تغییر پرداخت یا پیام به provider واقعی در این حالت startup را متوقف می‌کند.

سقف اولیهٔ تست خصوصی `PROVIDER_DAILY_BUDGET_RIAL=100000` (۱۰هزار تومان) و `OTP_MAX_COST_RIAL=10000` (هزار تومان) است؛ این‌ها سقف‌های محافظه‌کارانه‌اند، نه تعرفهٔ کاوه‌نگار. حداکثر۱۰رزرو کامل روزانه در بودجه جا می‌گیرد؛ سقف۳درخواست در۱۰دقیقه برای هر شماره و محدودیت نشست/CSRF نیز برقرار است. در هزینهٔ بیش از رزرو، کنترل هزینه ارسال‌های بعدی را متوقف می‌کند. رزرو قبلی/سقف ثبت‌شدهٔ پایین‌تر ممکن است ظرفیت باقی‌مانده را کمتر کند.

تنظیمات پس از شروع پردازش ثابت‌اند؛ بعد از تغییر `.env` فقط بک‌اند را با محیط جدید دوباره اجرا کنید. UI با `make dev-ui` و Fast Refresh فعال می‌ماند؛ image نسازید. از bootstrap یا health مقدار `otp_is_real=true` را بررسی کنید؛ هیچ شماره یا کلیدی در این پاسخ نیست. سپس در فرم ورود، شمارهٔ خود را وارد و «دریافت کد تأیید» را بزنید. تحویل واقعی فقط با دریافت روی گوشی بررسی می‌شود و از تست خودکار نتیجه نمی‌گیریم.

بازگشت: `LOCAL_REAL_OTP_ENABLED=0` و `OTP_BACKEND=demo`؛ سپس فقط بک‌اند را دوباره اجرا کنید. برای تغییر حالت، چالش‌های استفاده‌نشدهٔ قبلی را مصرف‌شده علامت بزنید تا کد قبلی مبنای تست تازه نشود. `python3 scripts/smoke.py` در حالت OTP واقعی، پیش از درخواست هر کد متوقف می‌شود؛ برای smoke ابتدا به demo برگردید. پایلوت و benchmark مصنوعی این استثنا را در پردازش جدا خاموش می‌کنند.

### خطای گواهی در پایتون محلی

اگر `ssl.get_default_verify_paths().cafile` خالی است و اتصال کاوه‌نگار با `SSLCertVerificationError` شکست می‌خورد، در اجرای نیتیو macOS می‌توان `SSL_CERT_FILE=/etc/ssl/cert.pem` را در `.env` خصوصی گذاشت؛ فایل باید CA معتبر سیستم باشد. پایتون آن را هنگام ساخت context امن می‌خواند. این مسیر میزبان را داخل کانتینر منتقل نکنید؛ Linux از CA خودش استفاده می‌کند. تأیید گواهی و نام میزبان را خاموش نکنید. نمونهٔ عمومیِ بدون کلید `https://api.kavenegar.com/v1/0/utils/getdate.json` برای بررسی TLS کافی است و پیامک نمی‌فرستد. مرجع: [SSL پایتون](https://docs.python.org/3/library/ssl.html#ssl.create_default_context).

از نسخه۰٫۸٫۴، شکست تأیید گواهی/DNS/رد اتصال پیش از ارسال با HTTP503 برمی‌گردد و چالش غیرقابل استفاده می‌شود. timeout یا پاسخ نامعلوم همچنان چالش را نگه می‌دارد، `delivery_status=unknown` برمی‌گرداند و خودکار تکرار نمی‌شود. خطای قطعی را با پذیرفته‌شدن پیامک یکی نگیرید. لاگ سرور فقط request ID و علت محدود و امن مثل `tls_certificate_verification_failed` یا پذیرش provider را ثبت می‌کند؛ متن خام خطای شبکه/URL کلیددار، شماره، کد و ورودی خصوصی ثبت نمی‌شود. دو رزرو آزمایشی قبلی با خطای TLS، محافظه‌کارانه در سقف روز باقی ماندند.

سقف روزانهٔ فعلی، حداکثر۵سفارش ساخته‌شده در ۲۴ ساعت گذشته است؛ سفارش پرداخت‌نشده یا لغوشده نیز حساب می‌شود تا رزرو مکرر باعث مزاحمت نشود. رزرو گیرنده تا۱۵دقیقه برای سفارش پرداخت‌نشده و تا تعیین نتیجه برای سفارش در صف فعال است. فاصلهٔ سراسری گیرنده و همان جفت فرستنده/گیرنده هردو۲۴ساعت‌اند؛ روز تقویمی و نیمه‌شب ملاک نیست. این کنترل‌ها در PostgreSQL و زیر قفل اعمال می‌شوند؛ کش، مبنای یکتای شمارش نیست. تست‌ها را با Redis database 15 اجرا کنید تا پاک‌کردن کش تست روی محدودیت‌های نمونهٔ در حال اجرا اثر نگذارد.

### ریست محدودیت برای تست ادمین

از نسخه۰٫۸٫۹، هر شمارهٔ تأییدشده یک‌بار۳ارسال رایگان دارد. migration0010 به حساب‌های موجود هم۳واحد می‌دهد و سفارش‌های قبلی را تغییر نمی‌دهد. مانده در فهرست حساب‌های ادمین فقط خواندنی است. ریست محدودیت آزمایشی، سهمیهٔ هدیه را شارژ نمی‌کند. پردازش `expire_unpaid_orders` رزروهای رایگان منقضی‌شده را آزاد می‌کند؛ beat/worker باید روشن باشند. سفارش رایگان تراکنش مالی ندارد، ولی اگر روزی ارسال واقعی با مجوزهای قبلی فعال شود هزینهٔ provider و سقف بودجه همچنان اعمال می‌شوند. وضعیت نامعلوم سهمیه را تا تعیین تکلیف نگه می‌دارد.

در محیط محلی، پس از migration، `DEMO_TEST_TOOLS_ENABLED=1` را در `.env` قرار دهید و پردازش‌های بک‌اند را یک بار با env جدید اجرا کنید. در این workspace فعال شده است. فرانت توسعه با Hot Reload روشن می‌ماند.

۱. در `/admin/` وارد حساب مدیر شوید و از بخش حساب‌ها، «ریست محدودیت آزمایشی» را باز کنید؛ مسیر مستقیم `/admin/core/account/test-limits/` است.
۲. شمارهٔ فرستنده‌ای که قبلاً در محصول وارد شده، شمارهٔ گیرندهٔ تست و دلیل کوتاه را وارد کنید. ارقام فارسی/عربی یکسان‌سازی می‌شوند.
۳. «ریست محدودیت برای تست» را بزنید و در محصول پیش‌نمایش تازه بسازید. شمارش۵سفارش فرستنده و فاصلهٔ سراسری گیرنده و همان جفت از زمان ریست شروع می‌شوند. پس از ارسال تازه، محدودیت دوباره برقرار است؛ ریست، حالت نامحدود دائمی نیست.

مدیر کل این مجوز را دارد؛ staff دیگر به `core.reset_demo_limits` و برای دیدن لینک فهرست حساب‌ها به مجوز مشاهدهٔ حساب نیاز دارد. GET تغییری نمی‌دهد و POST به CSRF نیاز دارد. سابقهٔ ریست در «ریست‌های محدودیت آزمایشی» و OperatorAudit ثبت می‌شود؛ شمارهٔ خام یا متن پیام در رکورد ریست ذخیره نمی‌شود.

ابزار فقط با `DEMO_MODE=1`، `SMS_BACKEND=console`، `PAYMENT_BACKEND=demo`، `PROVIDER_NETWORK_MODE=disabled` و `LIVE_PROVIDERS_ENABLED=0` کار می‌کند. در سایر حالت‌ها، هم ریست تازه ممنوع است و هم ریست‌های قبلی در شمارش نادیده گرفته می‌شوند. با خاموش‌کردن ابزار، شمارش عادی بر اساس سابقه برمی‌گردد. قطع دریافت، تعلیق، ارسال به خود، سفارش باز، ورود OTP و بودجهٔ پیامک تغییری نمی‌کنند. گیرندهٔ دارای سفارش باز باید ابتدا تعیین تکلیف شود؛ این ابزار سفارش، پرداخت یا وضعیت تحویل را حذف یا بازنویسی نمی‌کند. هیچ پیامک یا پرداختی با کلیک ریست انجام نمی‌شود.

### تنظیم ارسال و لحن هر حساب از نسخه۰٫۸٫۱۲

در `/admin/core/account/` حساب محصول خودت را از روی شمارهٔ پوشیده پیدا کن و شناسهٔ آن را باز کن. حساب محصول باید قبلاً با OTP ساخته شده باشد؛ ورود مدیر به‌تنهایی فرستندهٔ محصول نمی‌سازد. دو تیک مستقل در صفحهٔ حساب وجود دارند:

- **ارسال نامحدود برای تست:** سقف۵سفارش در۲۴ساعت، فاصلهٔ۲۴ساعتهٔ گیرنده/جفت و محدودیت کوتاه‌مدت preview/order برای همین فرستنده نادیده گرفته می‌شوند. لازم نیست پس از هر ارسال ریست بزنی. سفارش باز همان گیرنده باید تمام شود؛ ارسال بعدی را پس از رسید آزمایشی انجام بده.
- **لحن صریح‌تر و محترمانه:** پیام‌های خروجی همین حساب از مجموعهٔ متن‌های واضح‌تر انتخاب می‌شوند. مثلاً «بوی بدن شما در جمع محسوس است. لطفاً برای رفع آن، به شست‌وشوی بدن و تعویض لباس بیشتر توجه کنید.» حالت پیش‌فرض سایر حساب‌ها همچنان ملایم است. این تیک مربوط به فرستنده است و دریافت‌کننده را قضاوت یا دسته‌بندی نمی‌کند.

دلیل کوتاه تغییر را بنویس و ذخیره کن. تغییر هر تیک با مدیر، شناسهٔ حساب، مقدار قبل/بعد و دلیل در OperatorAudit ثبت می‌شود؛ شماره و متن خصوصی وارد این سابقه نمی‌شوند. مدیر کل مجاز است. staff دیگر برای دیدن حساب به `view_account` و برای هر گزینه به‌ترتیب به `core.manage_test_sending` یا `core.manage_message_tone` نیاز دارد؛ این مجوزها خودکار به گروه‌های پشتیبانی داده نمی‌شوند. GET تغییری ایجاد نمی‌کند و POST به CSRF نیاز دارد. شماره، هویت، تعلیق و اعتبار هدیه در این فرم قابل ویرایش نیستند.

تیک نامحدود فقط وقتی اثر دارد که تمام شروط ابزار آزمایشی بالا برقرار باشند. در محیط واقعی یا با خاموش‌شدن ابزار، حتی مقدار ذخیره‌شدهٔ true هم نادیده گرفته می‌شود؛ فعال‌کردن آن در آن محیط رد می‌شود و خاموش‌کردنش همیشه با مجوز ممکن است. غیرفعال‌کردن تیک، محدودیت عادی را فوراً بر اساس تاریخچه برمی‌گرداند؛ تاریخچه حذف یا ریست نشده است. این گزینه فقط محدودیت تعداد/فاصله را برمی‌دارد و سهمیهٔ۳ارسال رایگان را افزایش نمی‌دهد؛ ارسال‌های بعدی همچنان مسیر پرداخت آزمایشی دارند.

قطع دریافت، ارسال به خود، تعلیق/حذف حساب، سفارش باز گیرنده، کنترل محتوای ممنوع، توقف اضطراری، محدودیت OTP، کنترل کلی سیل درخواست IP و شروط هزینه/provider برقرارند. این تنظیم هیچ پیامک واقعی یا پرداختی را فعال نمی‌کند. برای تست این قابلیت، ریست بودجه یا OTP لازم نیست.

متن صریح هم پیش از تأیید به فرستنده نمایش داده می‌شود و پس از تأیید ثابت می‌ماند. تغییر تیک لحن، متن preview یا سفارش موجود را عوض نمی‌کند؛ برای دیدن لحن تازه پیش‌نمایش تازه بساز. فیلتر توهین/تهدید/اطلاعات خصوصی قبل و بعد از انتخاب متن برقرار است؛ مدل محلی هم فقط می‌تواند از متن‌های بررسی‌شدهٔ همان لحن انتخاب کند و اجازهٔ ارسال متن آزاد ندارد.

## مدل محلی اختیاری

برای مسیر پیش‌فرض، هیچ مدل یا GPU لازم نیست. اگر Ollama را از قبل روی دستگاه اجرا می‌کنید، `AI_MODE=ollama` و `OLLAMA_MODEL` را به مدلی که واقعاً نصب دارید تنظیم کنید. مقدار URL پیش‌فرض Compose به میزبان Docker اشاره می‌کند. برای دسترسی کانتینر، سرویس باید از شبکهٔ Docker قابل دسترس باشد؛ پورت مدل را عمومی نکنید.

```sh
docker compose up -d --force-recreate backend worker beat
```

مدل فقط موضوع و متن ورودی را می‌بیند؛ شماره تلفن در درخواست مدل نیست. خروجی به شناسهٔ یکی از متن‌های بررسی‌شده محدود می‌شود. قطعی یا پاسخ نامعتبر مدل باعث توقف پیش‌نمایش می‌شود. اجرای موفق این آداپتور با مدل نصب‌نشده ادعا نمی‌شود؛ تست پاسخ‌های ساختگی جای تست کیفیت مدل واقعی را نمی‌گیرد.

Celery با صف‌های event/control از نوع exclusive و پیام‌های task پایدار کار می‌کند. `acks_late` و `reject_on_worker_lost` فعال‌اند؛ outbox و قفل دیتابیس از پردازش تکراری دفاع می‌کنند. در RabbitMQ4.4 قابلیت منسوخ transient non-exclusive را فعال نکنید. اگر پس از ارتقا صف متوقف شد، image بک‌اند و worker را با هم بازسازی کنید.

## پشتیبان، بازیابی و عملیات نسخه۰٫۷

volume داده با `docker compose down` حذف نمی‌شود؛ برای توقف عادی از `down -v` استفاده نکنید. backup ساده SQL بدون رمز دیگر مسیر پیشنهادی نیست. ابزار `scripts/backup-restore.py` پشتیبان رمز‌شده0600 و restore فقط به DB تازه می‌سازد. کلید backup و کلید application جدا و خارج مخزن نگه داشته شوند. [راهنمای کامل](release-v0.7/RUNBOOK.fa.md) و [شاهد restore](release-v0.7/RESTORE.json) را دنبال کنید.

`python manage.py bootstrap_roles` نقش‌های حداقلی را بدون انتساب افراد می‌سازد؛ `ops_snapshot` شاخص‌های جمعی می‌دهد؛ `prune_private_data --dry-run` و `rotate_encryption` ابتدا بازبینی و سپس با دستور apply اجرا می‌شوند. HMAC شماره را بدون مهاجرت تغییر ندهید. `release_readiness --human-checks <path> --require-live-ready` موارد ناقص/انسانی را با exit غیرصفر رد می‌کند و مجوز انتشار صادر نمی‌کند.

## CI و اجرای محلی از GitHub

`ci.yml` روی push و PR بررسی بک‌اند و فرانت و یک چرخهٔ Compose را اجرا می‌کند. actionها به commit مشخص قفل شده‌اند؛ imageهای زیرساخت به شاخهٔ نسخه قفل هستند و patch آن‌ها ممکن است به‌روز شود. برای انتشار واقعی باید digest image و برنامهٔ به‌روزرسانی آسیب‌پذیری نیز ثبت شود.

`local-deploy.yml` فقط دستی و روی `main` اجرا می‌شود. runner باید مورد اعتماد، Linux و دارای Docker باشد و برچسب `begamnagam-local` داشته باشد. اجرای PR ناشناس روی آن مجاز نیست. `clean: false` کلید محلی را حفظ می‌کند؛ این workflow به محیط production یا ابر آروان متصل نیست. آزمون‌ها روی ماشین محلی اجرا می‌شوند؛ نتیجهٔ GitHub تا زمان push و اجرای workflow تأییدشده نیست.

## لینک کوتاه لغو در پیامک۰٫۸٫۱۳

در پیش‌نمایش تازه، آدرس بدون `https://` و با کد۸حرف/عدد ساخته می‌شود. APP_BASE_URL را همچنان HTTPS معتبر تنظیم کنید؛ scheme فقط هنگام ساخت متن پیامک حذف می‌شود و TLS، cookie و CSRF تغییری نمی‌کنند. پیام و لینک قدیمی با snapshot قبلی باقی می‌مانند. لینکِ ارسال‌شده بعد از پذیرش فعال می‌شود؛ همان صفحهٔ `/r` با fragment کوتاه کار می‌کند و migration یا تنظیم تازه لازم نیست.

برای تست، با حساب مصنوعی یک سفارش آزمایشی بسازید، سپس لینک را باز کنید؛ GET نباید دریافت را قطع کند. اقدام توقف نیازمند کلیک و POST با CSRF است. دریافت خودکار لینکِ بدون scheme روی گوشی واقعی هنوز پذیرش انسانی می‌خواهد. raw link و کد را وارد لاگ/تحلیل نکنید. محدودیت۱۲۰در۱۰دقیقهٔ IP علاوه بر۳۰در۱۰دقیقهٔ نشست و کد اعمال می‌شود. در CT، فقط peer پراکسی مشخص برای IP واقعی اعتماد می‌شود؛ XFF ورودی دلخواه را اعتماد نکنید.

برای rollback، نسخهٔ قدیمی۰٫۸٫۱۲ به‌تنهایی کدهای۸نویسه‌ای را قبول نمی‌کند. مسیر recipient را با پذیرش هر دو قالب نگه دارید؛ بازگشت کور به validator قدیمی، لینک‌های تازه را می‌شکند. کد۸نویسه‌ای و snapshot قبلی را بازنویسی نکنید؛ راه ایمن، اصلاح رو به جلو یا backport پذیرش هر دو قالب است.

## لینک ساده و موضوع‌های بیشتر۰٫۸٫۱۶

لینک پیامک تازه `begamnagam.ir/r/Ab12Cd34` است؛ کد۸نویسه‌ای از حروف انگلیسی و اعداد ساخته می‌شود. GET/HEAD بدون تغییر دریافت، به صفحهٔ `/r#Ab12Cd34` هدایت می‌شود. لینک‌های fragment قبلی معتبر می‌مانند. migration، شارژ دوبارهٔ هدیه، تغییر بودجه یا بازپخش پیام لازم نیست.

پیش از فعال‌کردن قالب تازه، مسیر `/r/` در تمام لایه‌های HTTP و HTTPS باید از ثبت URI خصوصی در access/error log و analytics مستثنا باشد. `no-store` و `no-referrer` جای این تنظیم را نمی‌گیرند. روی Nginx، فقط location همین مسیر را بررسی کنید؛ تنظیم proxy/headerهای فعلی را حفظ و از خاموش‌کردن لاگ کل سرور خودداری کنید. در این location، `access_log off;` و `error_log /dev/null;` مانع ثبت کد می‌شوند. redirect سراسری پورت۸۰، includeها و logهای دیگر نیز باید بررسی شوند. پیش از reload از config پشتیبان بگیرید، `nginx -t` را اجرا و با کد ساختگی `Ab12Cd34` پاسخ و نبودن آن در لاگ را کنترل کنید. مرجع: [ثبت درخواست در Nginx](https://nginx.org/en/docs/http/ngx_http_log_module.html) و [error_log](https://nginx.org/en/docs/ngx_core_module.html#error_log).

Traefik استقرار فعلی access log ندارد؛ runtime فرانت هم request access log فعال ندارد. در استقرار۰٫۸٫۱۶، روی Nginx مرکزی۱۹۲٫۱۶۸٫۱٫۶برای HTTP و HTTPS مسیر `/r/` لاگ بسته شد و location دقیق `= /r` روی HTTPS، مسیر fragment قبلی را حفظ می‌کند؛ بدون این location، Nginx به‌دلیل proxy location دارای اسلش، `/r` را خودکار۳۰۱می‌کند. config و reload و آزمون عملیِ نبودن کد ساختگی در access/error log موفق‌اند؛ درخواست کنترل عمومی همچنان ثبت می‌شود. بررسی نیازمند نشست root است؛ رمز یا کلید را در مخزن، چت یا فایل شواهد قرار ندهید. در استقرارهای دیگر تا تأیید این لایه، قالب path فعال نشود.

برای نمایش تمام۱۸موضوع، `PILOT_POSITIVE_ONLY=0` را در پروفایل مجاز سایت فعال تنظیم کنید؛ مقدار پیش‌فرض پروفایل خارجی همچنان محدود است. کنترل متن قبل و بعد از انتخاب الگو و در worker حفظ می‌شود. موضوع‌های بیشتر در UI با دکمهٔ باز/بسته در دسترس‌اند و موضوع انتخابی هنگام بستن فهرست پنهان نمی‌شود.

پذیرش بدون پیامک واقعی:

```sh
python3 scripts/verify-domain-routing.py --connect-ip 192.168.1.6 \
  --expect-live-gifts --expect-plain-recipient-links
```

برای rollback بعد از تولید لینک path، route جدید `/r/[code]` را نگه دارید یا همین redirect و هدرهای خصوصی را روی لبه نگه دارید؛ برگشت کامل فرانت۰٫۸٫۱۵ آن لینک‌ها را۴۰۴می‌کند. متن‌های تأییدشده و HMACها را تغییر ندهید.

## علت ارسال‌نشدن۰٫۸٫۱۷

رسید و سابقه از `status_reason` عمومی API استفاده می‌کنند. محدودیت حساب خود کاربر، سقف روزانه، فاصلهٔ ارسال خودش، شمارهٔ خودش، رد محتوا و انقضا توضیح روشن دارند. بازهٔ ارسال خارج از ساعت مجاز در Outbox ثبت و به کاربر گفته می‌شود؛ توقف فنی یا اپراتوری، دلیل ساعت قدیمی را دوباره نمایش نمی‌دهد. نتیجهٔ نامشخص همچنان نیازمند تطبیق است و نباید دوباره submit شود.

برای تشخیص علت فنی، `Outbox.last_error_code` و `MessageDelivery.last_error_code` در دادهٔ عملیاتی محفوظ‌اند. این کدها را مستقیماً به UI، API عمومی یا متن پشتیبانی کپی نکنید. دلیل عمومی فقط از فهرست مجاز انتخاب می‌شود؛ اعتبار پنل، بودجه و خطای provider پیام عمومی دارند و خطاهای۵xx هم جزئیات فنی نشان نمی‌دهند. سقف/ماندهٔ بودجه یا سهمیه در این انتشار reset نمی‌شود.

برای تست از دیتابیس مجزا و transport ساختگی استفاده کنید: محدودیت فرستنده، سه حالت هم‌ارز گیرنده، بازگشت یک‌بارهٔ هدیه، رد محتوای دستکاری‌شده، کمبود بودجه، انقضا، زمان ارسال و نتیجهٔ نامشخص. هویت و ترجیحات گیرنده نباید از مقایسهٔ پاسخ‌ها معلوم شود. rollback به۰٫۸٫۱۶به migration نیاز ندارد و فقط نمایش دلیل جدید را حذف می‌کند؛ از تغییر یا بازپخش سفارش‌ها خودداری کنید.

## جملهٔ آغاز پیام گیرنده۰٫۸٫۱۸

جملهٔ `نمیدونم بهت بگم یا نگم؟` و یک خط جدید در زمان ساخت پیش‌نمایش، قبل از متن بررسی‌شده قرار می‌گیرد. سقف۳بخش و لینک لغو حفظ می‌شوند؛ متن بلند با نمونهٔ کامل کوتاه‌ترِ همان موضوع/لحن جایگزین می‌شود و فرستنده همان را تأیید می‌کند. OTP ثابت، snapshotهای قبلی، بودجه و سهمیه تغییر نمی‌کنند. در adapter یا worker جمله را اضافه نکنید؛ retry باید دقیقاً همان متن قبلی را بفرستد. rollback به۰٫۸٫۱۷به migration یا بازنویسی داده نیاز ندارد و سفارش‌های دارای جمله همچنان همان snapshot را می‌فرستند.


## دعوت با شماره و جایزه۰٫۹٫۰

Migrationهای۰۰۱۳و۰۰۱۴ را قبل از بالا آوردن کد جدید اجرا کنید. DB constraint مانده را به۳به‌اضافهٔ مجموع جایزه محدود می‌کند؛ افزودن جایزه و افزایش `free_sends_earned_total` باید فقط از `reward_registration` در یک تراکنش انجام شوند. هدیهٔ حساب‌های موجود را reset نکنید. `reward_awarded_at` و audit `invitation_reward` مرجع یک‌باربودن جایزه‌اند. حذف حساب دعوت‌کننده، افزودن جایزهٔ تازه را متوقف می‌کند؛ تعلیق، مصرف سهمیه را می‌بندد.

`reconcile_outbox` دعوت‌های pending و جایزهٔ ثبت‌نشده را بازیابی می‌کند. `reconcile_providers` فقط نتیجهٔ submitting/accepted/unknown را با localid/reference استعلام می‌کند. هیچ وضعیت نامعلوم، نبود localid یا timeout مجوز submit دوم نیست. هر درخواست ارسال‌نشده پس از۴۸ساعت منقضی می‌شود. پنل مدیریت دعوت و نوبت‌ها فقط‌خواندنی و بدون شمارهٔ کامل/متن/capability است؛ کلیدها و خام خطای provider عمومی نمی‌شوند.

دعوت، همان halt، محدودیت ساعت، قطع دریافت و سقف gross روزانهٔ provider را رعایت می‌کند؛ SMS_MAX_COST_RIAL سقف رزرو هر دعوت است. کمبود بودجه درخواست pending را تا بازهٔ روز بعد به تعویق می‌اندازد و جزئیات پول/سیستم را به کاربر نمی‌دهد. بودجه برای آزمون افزایش یا reset نشود. پیام دعوت سهمیهٔ حساب را مصرف نمی‌کند. Nginx و مسیر محافظت‌شدهٔ /r/ موجود کافی‌اند و تغییری لازم نیست.

پاک‌سازی۹۰روزهٔ شماره و snapshot دعوت تعیین‌تکلیف‌شده و re-encryption در فرمان‌های موجود پوشش دارند؛ claim HMAC و سابقهٔ جایزه می‌مانند. unknown/accepted حل‌نشده و hold گزارش حفظ می‌شوند. فقط برای پنل دعوتِ احرازشده، اعلام عضویت قبلی و نتیجهٔ ثبت‌نام با دستور کارفرما مجاز است؛ ارسال پیام معمول همچنان این داده را افشا نمی‌کند.

Rollback نرم‌افزار را با schema افزوده و مانده‌ها انجام دهید؛ migration معکوس پس از مصرف دعوت و جایزه مجاز نیست. ابتدا pending/unknown دعوت‌ها را تعیین تکلیف کنید؛ لینک لغو /r/ در نسخهٔ۰٫۸٫۱۸ کار می‌کند، اما UI قدیم مجموع جایزه را نمی‌شناسد. نسخهٔ ۰٫۱۲٫۱ سرور با gpt-4.1-mini فعال است؛ پس از رخداد پاسخ ناقص reasoning در Luna، مدل با آزمون واقعی محلی و سرور عوض شد. سقف روزانهٔ هر حساب ۱۰ و سقف کل سایت فعلاً نامحدود است؛ ادمین از «تنظیمات سایت» ← «بازنویسی GapGPT» می‌تواند گزینهٔ بدون سقف را خاموش و سقف دلخواه را تعیین کند. مقدار عددی قبلی ۲۰ حفظ شده و با روشن‌بودن گزینه اعمال نمی‌شود. کلید خصوصی، مصرف قبلی، اعتبارها و سایر تنظیمات حفظ شده‌اند؛ ریست درخواستی حساب لوکال روی سرور تکرار نشد. حالت پیش‌فرض مخزن همچنان template با سقف صفر است. کلید، مدل، سهمیهٔ مثبت هر حساب و سقف مثبت سایت یا گزینهٔ بدون سقف، همراه انتخاب provider در تنظیمات نسخه‌دار لازم‌اند. تنظیم ذخیره‌شدهٔ پنل بر env اولویت دارد. OTP/SMS واقعی و کلیدهای خاموش پرداخت حفظ شده‌اند. [راهنمای اتصال، هزینه و نتیجهٔ آزمون](ai-gapgpt.fa.md) و [شواهد انتشار](deployments/ct115-0.12.1.json).

هر بازنویسی حداکثر دو تماس با۲۵۶توکن خروجی برای هر تماس دارد؛ سقف کل۵۱۲توکن است و reasoning گزارش‌شدهٔ Gateway را هم شامل می‌شود. تولید و بازبینی مستقل حفظ شده‌اند؛ هیچ پاسخ ناقص یا تأیید نامطمئن به ارسال نمی‌رسد. endpoint ثابت https://api.gapgpt.app/v1 است، retry یا fallback خودکار وجود ندارد و سهمیهٔ مصرف‌شده با خطا برنمی‌گردد. سقف تعداد و خروجی، ادعای مبلغ قطعی قبض نیست. بودجه و پیامک/OTP مستقل‌اند.

## بازنویسی محلی بلادرنگ و انتخاب سرویس

[راهنمای Ollama](ai-ollama.fa.md) قرارداد بلادرنگ، نصب مدل در Docker، سهم منابع، انتخاب Ollama/GapGPT در هر دو پنل، مجوز `manage_ai` و آزمون‌های ساختگی بدون پیامک را توضیح می‌دهد. روی CT، فایل `compose.ollama.yaml` پس از دو فایل داخلی و hardened قرار می‌گیرد. فعال‌سازی مدل به بررسی خروجی واقعی و تأخیر روی CPU وابسته است؛ ساخت image یا موفقیت تست mock، تأیید کیفیت مدل نیست.

## بسته‌های اعتبار پیام

مدیریت بسته، snapshot خرید، تطبیق پرداخت و برگشت اعتبار در [راهنمای بسته‌ها](message-packages.fa.md) آمده است. مهاجرت0022 را پیش از وب/worker جدید اعمال کنید. پرداخت واقعی با فعال‌کردن بسته فعال نمی‌شود. سفارش‌ها/رسیدهای قدیمی و دادهٔ اعتبار را حذف یا replay نکنید.

## مستندات خصوصی API مصرف‌کنندگان جدید

`/api/v2/document` فقط با `API_DOCUMENTATION_ENABLED=1` و نشست حساب فعال
دارای مجوز `core.view_api_documentation` در دسترس است؛ superuser نیز دسترسی
دارد. فرانت‌کار از `/api/v2/document/login` وارد می‌شود؛ حسابش فقط همین مجوز
را دارد، staff/superuser خاموش و فاقد Account تلفنی است. مجوز یا خود حساب
را می‌توان برای قطع دسترسی غیرفعال کرد. نشست۸ساعته، محدودیت ورود و CSRF
ورود/خروج برقرارند. مهاجرت `0036` مجوز را تعریف می‌کند و خودکار به کسی نمی‌دهد.
schema، راهنما، کلاینت نمونه و assetها همین شرط را دارند. پس از تحویل به
فرانت، متغیر را0کنید؛ API محصول برقرار می‌ماند. Compose این متغیر را به بک‌اند
می‌رساند؛ محیط نیتیو/انتشار باید آن را در env خصوصی بک‌اند تنظیم کند.
