# پیکربندی ظرفیت۰٫۱۱٫۲ — تقسیم رندر بین شش فرانت

پروفایل سه‌فرانت [۰٫۱۱٫۱](../release-v0.11.1-capacity/README.fa.md) در۳۲۵و۴۰۰RPS بدون افت گذشت، ولی در۴۲۵/۴۵۰ افزایش تأخیر و افت ورودهای ابزار داشت. برای بررسی گلوگاه رندر، تنها تعداد فرانت‌ها از۳به۶افزایش یافت؛ backend/داده/صف و imageها تغییر نکردند. این مقایسه روی همان مسیر HTTPS دامنه انجام شد. پس از تشخیص محدودیت Nginx مرکزی، upstream keepalive و Upgrade شرطی روی همان دامنه فعال شد؛ گزارش نهایی هر دو لایه را پوشش می‌دهد.

پروفایل نهایی `compose.performance.yaml` شش Node هم‌ساخت روی loopback۳۰۰۰تا۳۰۰۵، هرکدام۷۶۸MiB و heap۳۸۴MiB، و Traefik۵۱۲MiB با GOMEMLIMIT۳۸۴MiB دارد. backend سه worker،هرکدام دو thread و۷۶۸MiB، worker۲۵۶MiB وbeat۱۹۲MiB باقی‌اند. مجموع سقف۱۳سرویس۶٬۷۵۲MiB است؛ مصرف واقعی با این سقف برابر نیست. PostgreSQL/Redis/RabbitMQ و volumeها recreate نشده‌اند؛ migration یا تغییر provider انجام نشده است.

همهٔ فرمان‌های Compose این انتشار، از جمله recreate بعدی، باید سه فایل داخلی، hardened و performance را داشته باشند. [راهنمای اجرا و بازگشت پروفایل قبلی](../release-v0.11.1-capacity/README.fa.md) معتبر است؛ برای بازگشت سه‌فرانت، ابتدا routing قبلی فعال و سپس frontend4/5/6 متوقف شوند. current و پوشهٔ bindشدهٔ dynamic پراکسی برای اعلان تمدید TLS باید هماهنگ بمانند. image تمام شش فرانت در هر انتشار بعدی باید یکسان باشد.

آزمون مرحله‌ای و۳۰دقیقه‌ای کامل شد؛ گزارش نهایی زیر مرجع نتیجه است.

**نتیجهٔ نهایی:** [گزارش پس از اصلاح Nginx و آزمون۳۰دقیقه‌ای](../performance-2026-10-28/optimized.fa.md) کامل شده است؛ تنظیمات بالا روی سرور فعال‌اند.
