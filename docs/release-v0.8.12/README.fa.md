# نسخه۰٫۸٫۱۲ — تنظیمات ارسال هر حساب

دو تیک در صفحهٔ هر حساب محصولِ مدیریت اضافه شد: «ارسال نامحدود برای تست» و «لحن صریح‌تر و محترمانه». هر دو پیش‌فرض خاموش‌اند. از فهرست `/admin/core/account/` حساب خودت را پیدا کن، شناسه را باز کن، تیک دلخواه و دلیل کوتاه را وارد و ذخیره کن. تیک لحن برای پیام‌های خروجی فرستنده است؛ روی تمام حساب‌ها اعمال نمی‌شود.

نامحدود آزمایشی سقف روزانه، فاصلهٔ گیرنده/جفت و سقف کوتاه‌مدت پیش‌نمایش/ثبت سفارش همان حساب را کنار می‌گذارد. سفارش باز گیرنده باید تمام شود؛ پس از رسید آزمایشی دوباره ارسال کن. این قابلیت فقط با روشن‌بودن ابزار و بسته‌بودن پرداخت/ارسال واقعی اثر دارد. در حالت واقعی، حتی مقدار ذخیره‌شدهٔ true نادیده گرفته می‌شود. خاموش‌کردن تیک، محدودیت را بر اساس تاریخچهٔ دست‌نخورده برمی‌گرداند.

تأیید OTP، قطع دریافت، ارسال به خود، تعلیق/حذف حساب، سفارش باز، کنترل سیل درخواست IP، توقف اضطراری، بودجه و سهمیهٔ۳ارسال رایگان حفظ شده‌اند. این گزینه سهمیه را شارژ نمی‌کند و provider واقعی فعال نمی‌کند.

نمونهٔ لحن صریح‌تر:

> بوی بدن شما در جمع محسوس است. لطفاً برای رفع آن، به شست‌وشوی بدن و تعویض لباس بیشتر توجه کنید.

متن همچنان از مجموعهٔ بررسی‌شده انتخاب می‌شود؛ توهین، تهدید و اطلاعات خصوصی پیش و پس از بازنویسی رد می‌شوند. Ollama فقط می‌تواند شناسهٔ متن همان لحن را انتخاب کند. Worker هر دو مجموعهٔ بررسی‌شده را اعتبارسنجی می‌کند. پیش‌نمایش و سفارش قبلی با تغییر تیک بازنویسی نمی‌شوند؛ ارسال همان متن تأییدشده است.

مدیر کل مجاز است. staff به مجوز مشاهدهٔ حساب و برای هر تیک به‌ترتیب `manage_test_sending` و `manage_message_tone` نیاز دارد. تغییرها با CSRF، دلیل و سابقهٔ مدیر/قبل/بعد ثبت می‌شوند. هویت، شماره، ماندهٔ هدیه و وضعیت تعلیق در فرم تنظیمات فقط خواندنی‌اند. نقش‌های موجود خودکار مجوز جدید نگرفته‌اند.

## بررسی

- ۱۴۵ تست کامل روی PostgreSQL موفق؛ شامل۲۲تحویل پیاپی از حساب تست، حفظ محدودیت دیگران، خاموش‌کردن فوری، مجوز مستقل، CSRF، حفظ OTP و قطع دریافت.
- مجموعهٔ۱۲۰ورودی کنترل محتوا برای هر دو لحن بررسی شد؛ پاسخ آزاد یا شناسهٔ نامعتبر مدل رد می‌شود.
- migrationهای0011 و0012 با پیش‌فرض false برای برنامه و دیتابیس اضافه شدند؛ بررسی تطابق migration موفق است. INSERT حساب با ستون‌های نسخهٔ قدیمی هم آزموده شد.
- روی CT، ورود ادمین با گواهی معتبر، نمایش و ذخیرهٔ تیک‌ها، دلیل اجباری و دو سابقهٔ تغییر با حساب مصنوعی بررسی شد. شش ارسال پیاپی به یک گیرنده از RabbitMQ/Celery به delivered_demo رسید؛ سه سفارش اول هدیه و سه سفارش بعد پرداخت شبیه‌سازی‌شده بودند. سپس هر دو تیک حساب مصنوعی خاموش و نشست تشخیصی باطل شد.
- هیچ OTP یا پرداخت واقعی ایجاد نشد. حالت پیش‌فرض و تنظیمات واقعی قبلیِ OTP دست‌نخورده‌اند.
- مسیر HTTPS دامنه از Nginx داخلی، assetها، API و کوکی/CSRF دوباره موفق بود. فرانت و سرویس‌های داده recreate نشدند؛ proxy برای اتصال mount پیکربندی به release جدید recreate شد تا تمدید گواهی در آینده reload را به مسیر فعال بفرستد.
- UI جدید React/CSS ندارد؛ native Hot Reload فرانت روشن ماند و image فرانت ساخته نشد. این دور بررسی بصری مرورگر/گوشی انجام نشد؛ فرم استاندارد Django از طریق HTTPS واقعی بررسی شد. پذیرش انسانی گوشی/PWA همچنان محفوظ است.

[شواهد استقرار CT](../deployments/ct115-0.8.12.json) و [راهنمای کامل مدیریت](../operations.md#تنظیم-ارسال-و-لحن-هر-حساب-از-نسخه۰۸۱۲) جزئیات را دارند. Context7 ابزار قابل‌فراخوانی نداشت؛ از [مستندات رسمی Django Admin](https://docs.djangoproject.com/en/5.2/ref/contrib/admin/) و [پیش‌فرض دیتابیس](https://docs.djangoproject.com/en/5.2/ref/models/fields/#db-default) استفاده شد.

## بازگشت

نسخهٔ قبلی `/opt/begamnagam/releases/0.8.11-traefik` و env/imageهایش محفوظ‌اند. مسیر backup دقیق در شواهد آمده است. برای بازگشت، ابتدا سفارش‌های باز با لحن صریح را تعیین تکلیف کنید؛ worker نسخهٔ قبل آن متن‌ها را نمی‌شناسد. current را به release قبلی برگردانید و از همان دایرکتوری، `docker compose --env-file .env.internal -f compose.internal.yaml up -d --no-deps --force-recreate backend worker beat proxy` را اجرا کنید. دیتابیس و فرانت را تغییر ندهید و migrationها را unapply نکنید؛ ستون‌ها پیش‌فرض دیتابیس false دارند و با INSERT نسخهٔ قدیم سازگارند. نسخهٔ قدیمی تیک‌های ذخیره‌شده را به کار نمی‌برد. هیچ volume حذف نشده است.
