# نسخه۰٫۸٫۱۳ — لینک کوتاه لغو

قالب جدید پیامک `begamnagam.ir/r#A7k2P9xQ` است: پیشوند `https://` فقط از متن پیامک حذف و کد۴۳نویسه‌ای با۸حرف/عدد تصادفی عوض می‌شود. آدرس نمونه۲۴نویسه و نسبت به قالب قبلی۴۳نویسه کوتاه‌تر است. HTTPS واقعی برنامه، CSRF، کوکی و APP_BASE_URL تغییر نمی‌کنند. تعداد بخش پیامک از کل متن نهایی محاسبه می‌شود؛ کوتاه‌شدن لینک الزاماً همهٔ موضوع‌ها را به دو بخش تبدیل نمی‌کند.

کد از حروف انگلیسی بزرگ/کوچک و اعداد با secrets تولید می‌شود و به شماره یا شناسهٔ ترتیبی وابسته نیست. فقط HMAC آن در lookup نگهداری می‌شود. unique دیتابیس جلوی برخورد هم‌زمان را می‌گیرد؛ برخورد در savepoint با کد تازه تکرار و پس از۵شکست، کل پیش‌نمایش rollback می‌شود. کدهای۴یا۶نویسه‌ای تولید/پذیرفته نمی‌شوند. انتخاب۸نویسه، فضای حدس را از۴/۶بزرگ‌تر نگه می‌دارد؛ این فضای حدود۴۷٫۶بیتی هم‌ارز قابلیت۲۵۶بیتی قبلی نیست.

لینک فقط پس از پذیرش ارسال فعال می‌شود. انقضای۳۶۵روز توقف/۳۰روز گزارش، جلوگیری از افشای هویت/متن، اجرای صرفاً POST با CSRF و عدم تغییر با GET حفظ شده‌اند. محدودیت۱۲۰در۱۰دقیقهٔ IP به۳۰در۱۰دقیقهٔ نشست و کد افزوده شد؛ تغییر نشست یا کد آن را دور نمی‌زند. حساب تست نامحدود هم از این کنترل لغو مستثنا نیست. در CT، IP از پراکسی‌های مشخص استخراج می‌شود؛ XFF دلخواه مورد اعتماد نیست.

fragment همچنان به access log یا query/path نمی‌رود. snapshot دارای لینک در Preview/Order رمز شده و پس از تأیید ثابت است. لینک‌های۴۳نویسه‌ای قبلی و متن‌های قبلی بازنویسی نمی‌شوند و همان handler آن‌ها را می‌پذیرد. برای پیام ارسال‌شدهٔ منقضی، پاک‌سازی اتصال گیرنده را حذف ولی digest نامفهوم کد را رزرو نگه می‌دارد تا همان کد به گیرندهٔ دیگری اختصاص پیدا نکند.

## بررسی

۱۵۱تست کامل روی PostgreSQL موفق‌اند، شامل قالب۸نویسه و bare domain، snapshot رمز‌شده، CSRF، انقضا، گزارش، حفظ لینک قدیمی با scheme قبلی، برخورد تصادفی/تکراری، rollback کامل در شکست صدور، عدم تخصیص دوباره پس از پاک‌سازی، و تلاش با نشست‌ها/کدهای عوض‌شده زیر یک IP. تطابق migration بررسی شد؛ تغییر مدل یا migration تازه وجود ندارد.

برای پذیرش CT، پیش از ارتقا با نسخه۰٫۸٫۱۲ یک لینک۴۳نویسه‌ای در تحویل کاملاً آزمایشی ساخته شد. پس از ارتقا، همان لینک و hash متن ثابت سفارش بررسی و سپس یک لینک کوتاه تازه از API واقعی ساخته و با RabbitMQ/Celery تحویل آزمایشی شد. هر دو لینک با درخواست CSRFدار روی HTTPS معتبر، توقف دریافت را انجام دادند. هیچ OTP واقعی، درخواست پرداخت یا پیامک واقعی ایجاد نشد. نشست تشخیصی باطل و fixture خصوصی حذف شد.

فرانت تغییر نکرد، image آن دوباره ساخته نشد و Hot Reload توسعه روشن ماند. صفحهٔ فعلی `/r` از ابتدا fragment را بدون اجبار طول۴۳می‌خواند. بررسی تشخیص خودکار bare URL در SMS گوشی واقعی همچنان پذیرش انسانی است؛ HTTP یا تست مصنوعی این رفتار دستگاه را ثابت نمی‌کند.

[شواهد استقرار CT](../deployments/ct115-0.8.13.json)، [قرارداد API](../api.md#لینک-کوتاه-لغو۰۸۱۳) و [راهنمای نگهداری](../operations.md#لینک-کوتاه-لغو-در-پیامک۰۸۱۳) مرجع‌اند. Context7 ابزار قابل‌فراخوانی نداشت؛ مستندات رسمی [secrets](https://docs.python.org/3/library/secrets.html) و [تراکنش‌های Django](https://docs.djangoproject.com/en/5.2/topics/db/transactions/) استفاده شد.

## بازگشت

پشتیبان release و env پیش از تغییر نگه داشته شده است. بازگشت کور به image۰٫۸٫۱۲، validator۴۳نویسه‌ای را برمی‌گرداند و لینک کوتاه تازه را می‌شکند. برای rollback باید پذیرش هر دو قالب در مسیر recipient حفظ یا backport شود؛ اصلاح رو به جلو ترجیح دارد. داده، hash کد و snapshot را بازنویسی نکنید و هیچ volume یا migration را حذف نکنید. فرانت و سرویس‌های داده در استقرار دست‌نخورده‌اند؛ mount پروکسی به release جدید متصل می‌شود تا تمدید گواهی همچنان reload معتبر داشته باشد.
