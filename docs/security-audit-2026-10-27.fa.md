# بررسی امنیت و هاردنینگ — ۲۰۲۶-۱۰-۲۷

این سند بررسی اولیهٔ کد، آزمون‌های ایزولهٔ PostgreSQL/Redis، HTML دامنه و CT فعال را ثبت می‌کند. آن مرحله صرفاً خواندنی بود. پس از درخواست صریح کارفرما، اصلاحات در۰٫۱۱٫۰ اعمال شدند؛ [گزارش انتشار و موارد باز](release-v0.11.0/README.fa.md) وضعیت پس از تغییر را نشان می‌دهد. برای بررسی و انتشار هیچ OTP یا پیامک واقعی ارسال نشد. اطلاعات اتصال و مقادیر کلیدها در گزارش نیامده‌اند.

**یافتهٔ اولیه: دسترسی سرویس‌های داخلی نیاز به هاردنینگ داشت؛ این دسترسی‌ها اکنون در۰٫۱۱٫۰ اصلاح شده‌اند.** مهم‌ترین خطر اولیه، دسترسی جانبی پس از نفوذ به یکی از فرایندهای همین CT بود؛ سرویس‌های داده فقط به loopback متصل‌اند. آزمون مستقل از شبکهٔ بیرونی برای تمام پورت‌های NAT انجام نشده است.

## کنترل‌های بررسی‌شده و برقرار

- DB، Redis، AMQP، ارتباط داخلی RabbitMQ، metrics، backend و frontend روی127.0.0.1 هستند. ورودی Traefik روی IP مشخص CT و پورت۸۰/۴۴۳ است؛ SSH استثنای رابط عمومی میزبان است. این شاهد، جای بررسی NAT و firewall بیرونی را نمی‌گیرد.
- کانتینرهای برنامه و proxy غیرprivileged، با filesystem فقط خواندنی، حذف capabilityها و بدون mount کردن Docker socket اجرا می‌شوند. writable بودن volume داده برای DB/صف لازم است.
- `DEBUG=false`، کوکی نشست Secure/HttpOnly، کوکی CSRF Secure، CSRF فعال و دامنه‌های مجاز مشخص هستند. API سابقه بدون ورود۴۰۱ و عملیات بدون نقش staff مناسب۴۰۳ می‌دهد. ورود ادمین به‌تنهایی حساب محصول محسوب نمی‌شود.
- سفارش، رسید و دعوت‌ها با owner حساب محدود می‌شوند. آزمون‌های مالکیت بین دو نشست/کاربر، idempotency، رقابت روی قفل PostgreSQL و جلوگیری از ارسال دوباره در مجموعهٔ تست موجود پوشش دارند.
- OTP تصادفی، موقت، تک‌مصرف و وابسته به نشست است؛ مقدار خام آن ذخیره نمی‌شود و بررسی با HMAC/مقایسهٔ ثابت انجام می‌شود. ورود نشست/CSRF را می‌چرخاند. بازفعال‌سازی دریافت و درخواست حذف به تأیید تازهٔ شماره نیاز دارند.
- شماره‌ها رمز و شناسه‌های تطبیق با HMAC ذخیره می‌شوند. نام و شمارهٔ فرستنده به گیرنده نمایش داده نمی‌شود. افشای عضویت فقط در پنل دعوتِ احرازشده، مطابق تصمیم صریح محصول، مجاز است.
- لینک گیرنده فقط اختیار محدود توقف/گزارش دارد و محتوا، شماره یا هویت را نشان نمی‌دهد. GET/HEAD تغییر ترجیحات نمی‌دهند؛ اقدام‌ها POST و وابسته به CSRF هستند. کوتاه‌بودن کد۸نویسه‌ای به معنی داشتن قدرت توکن نشست یا لینک خواندن پیام نیست.
- payload taskها شناسه‌هاست؛ صف محل متن خصوصی/OTP/شماره نیست. JSON تنها قالب مجاز سلری است. outbox، وضعیت submission، قفل‌ها و نتیجهٔ unknown جلوی replay کورکورانه را می‌گیرند. سفارش لغوشده replay نمی‌شود.
- Service Worker فقط fallback عمومی و آیکون‌های allowlist را نگه می‌دارد؛ API، پاسخ RSC، متن خصوصی و درخواست mutating را cache یا replay نمی‌کند.
- فایل‌های `.env`، `.env.internal`، `.git/config`، SQLite، backup SQL و source سرور از HTTP قابل دریافت نبودند. CSS مدیریت و JS/CSS/تصاویر عمومی باید قابل دریافت بمانند؛ مخفی‌کردن assetهای عمومی کنترل دسترسی محسوب نمی‌شود.
- دو فایل env شناسایی‌شده روی CT مجوز0600 دارند. اسکن فایل‌های tracked و خروجی JS عمومی با کلیدهای خصوصی شناخته‌شدهٔ همین محیط تطبیقی پیدا نکرد؛ source map عمومی هم دیده نشد. این اسکن ادعای پوشش همهٔ کلیدهای تاریخی Git نیست.
- endpointهای provider محدود به مقصدهای بررسی‌شده‌اند، TLS verification خاموش نیست، timeout/اندازهٔ پاسخ محدود است و پاسخ نامعلوم موفقیت یا مجوز ارسال مجدد تلقی نمی‌شود. بازنویسی AI تا پالایش، بازبینی و تأیید دقیق preview به adapter نمی‌رسد.

## اصلاحات تهیه‌شده در کد و منتشرشده در۰٫۱۱٫۰

1. Redis با `core.cache.JSONSerializer` کار می‌کند؛ pickle هرگز اجرا نمی‌شود. شمارنده‌های عددی برای INCR اتمیک سازگار مانده‌اند و timeout اتصال/فرمان۳ثانیه است. Redis تولید را برای این تغییر FLUSH نکنید؛ شمارنده‌ها حفظ می‌شوند و مقدار قدیمی غیرعددی در صورت برخورد، fail closed می‌شود.
2. تلاش ورود ادمین، مستقل از نشست و محدودیت‌های قابل‌ویرایش محصول، به۱۰تلاش برای IP/نام کاربری و۵۰تلاش برای IP در۶۰۰ثانیه محدود می‌شود. رمز خوانده یا log نمی‌شود. تغییر نشست/نام کاربری به‌تنهایی دورزننده نیست؛ خرابی cache ورود را با۵۰۳ می‌بندد. پاسخ۴۲۹ دارای `Retry-After` است. این جای MFA یا دفاع در برابر حملهٔ توزیع‌شده را نمی‌گیرد.
3. CSP بک‌اند فقط scriptهای همان origin را مجاز می‌کند؛ object/frame/base بسته‌اند. CSP فرانت برای هر درخواست nonce تصادفی۲۵۶بیتی می‌سازد، هدر جعلی ورودی را بازنویسی می‌کند و تمام scriptهای Next و JSON-LD را با همان nonce رندر می‌کند. script inline بدون nonce و eval در production مجاز نیست. inline CSS برای styleهای React/ویجت‌ها حفظ شده است. CSP صفحهٔ آفلاین جداست و script ندارد.
4. HTML فرانت با nonce به‌صورت پویا و `private, no-store` رندر می‌شود. این انتخاب هزینهٔ SSR را نسبت به HTML استاتیک بیشتر می‌کند؛ static assetها cacheable می‌مانند. robots و sitemap استاتیک‌اند. دامنه و flag سئو همچنان در build تثبیت می‌شوند تا image بدون env زمان اجرا هم canonical درست بدهد.
5. HSTS روی خروجی production با مبدأ HTTPS، فقط با `max-age=31536000` اضافه می‌شود؛ includeSubDomains/preload فعال نشده است. کوکی/پروفایل پیامک و پرداخت تغییر نکرده‌اند.
6. remote control و task events سلری خاموش و قالب نتیجه نیز JSON شده است. این تغییر بدون انتشار worker جدید، وضعیت worker فعال را تغییر نمی‌دهد؛ ابزارهایی مثل `celery inspect` که به remote control وابسته‌اند دیگر معیار سلامت این پروفایل نیستند.
7. `sslmode` و گزینه‌های گواهیِ DSN دیتابیس دیگر نادیده گرفته نمی‌شوند. `connect_timeout` پیش‌فرض۵ثانیه است؛ گزینهٔ ناشناخته/تکراری یا timeout نامحدود startup را متوقف می‌کند. برای ارتباط غیرمحلیِ نامطمئن از `verify-full` و CA معتبر استفاده شود؛ صرف `sslmode=require` هویت میزبان را کامل تأیید نمی‌کند.
8. پروفایل non-demo کلید HMAC یکسان با secret/encryption و کلید رمزنگاری مشتق‌شده از secret پیش‌فرض را نمی‌پذیرد. هیچ کلید فعلی خودکار تعویض نشده است. HMAC key را بدون طرح حفظ تطبیق حساب‌ها و suppression عوض نکنید.
9. migration0017 بدنه‌های موجود را بدون تغییر محتوای بررسی‌شده رمز می‌کند؛ rollback صریح داده را به قالب قبلی برمی‌گرداند. چرخش کلید هر دو فیلد جدید را هم پوشش می‌دهد. بکاپ‌های قدیمی همچنان تابع سیاست نگهداری‌اند و صرف مهاجرت، نسخه‌های قدیمی را پاک نمی‌کند.
10. بدنهٔ بیش از۸۱۹۲بایت API با۴۱۳، پیش از فراخوانی provider، رد می‌شود. ValueError غیرمنتظره به متن عمومی تبدیل می‌شود؛ پیام‌های اعتبارسنجی مشخص در allowlist حفظ شده‌اند.
11. dependency رمزنگاری به50.0.2 و ابزار wheel cache هماهنگ شده است. `.dockerignore`ها ورود envهای فرعی، کلید خصوصی و دیتابیس محلی به build context را منع می‌کنند.
12. مسیر مدیریت جدید `/manage` نیز private/noindex است؛ API آن CSRF، احراز staff و مجوز هر منبع/عملیات را بررسی می‌کند و فهرست رکوردها، شماره/متن پیام/توکن خصوصی را کنار می‌گذارد. خواندن جزئیات گزارش فقط با مجوز مشخص، دلیل و ثبت audit مجاز است. ورود این پنل محدودیت جداگانهٔ۲۰تلاش برای IP و۸تلاش برای نشست در۶۰۰ثانیه دارد. تغییر موفق نشست محصول یا مدیریت، دادهٔ خصوصی تب‌ها را پاک می‌کند؛ پنل مدیریت هنگام بازگشت به تب اعتبار نشست را دوباره می‌خواند و پاسخ نشست قدیمی را نمایش نمی‌دهد.

## وضعیت اقدامات عملیاتی پس از مجوز انتشار

- **pg_hba، roleها، DSN، Redis ACL، حساب/vhost صف، firewall و SSH اصلاح شدند.** رمز مدیر سرویس‌ها از env برنامه کنار گذاشته شد. محدودکنندهٔ ورود وب فعال است؛ MFA وب هنوز نیازمند ثبت عامل اپراتور است.
- فایروال اختصاصی CT اکنون input با policy=`drop` دارد و پس از تأیید SSH تازه با کلید و HTTPS ماندگار شد. قواعد Docker flush نشدند؛ HTTP فقط از edge و SSH/TLS از LAN مجازند. host networking همچنان محدودیت مستند LXC است.
- مسیر ثبت‌شدهٔ Nginx مرکزی تا CT از HTTP شبکهٔ خصوصی استفاده می‌کند. برای شبکه‌ای که مرز اعتماد کافی ندارد، TLS با CA معتبر/تأیید هویت بین edge و CT لازم است. پیکربندی جاری Nginx مرکزی با SSH این نشست قابل خواندن نبود؛ اعتماد به forwarded headers و حذف URI توکن از access/error log آن لایه باید دوباره به‌صورت مستقل تأیید شود. غیرفعال‌کردن لاگ کل سایت پیشنهاد نمی‌شود.
- بکاپ رمز‌شده پیش از تغییر و snapshot نهایی در توقف نویسنده‌ها گرفته شد؛ restore قبل و بعد از انتشار موفق بود. بکاپ روزانه و rehearsal هفتگی فعال و یک‌بار موفق اجرا شدند. archive رمز‌شده و کلید جداگانه روی دستگاه اپراتور کپی شدند؛ replication خودکار خارج میزبان و سیاست نگهداری هنوز بازند. صحت job پاک‌سازی/clearsessions در حال اجرا نیز باید پایش شود.
- سقف هزینهٔ روزانهٔ پروفایل هدیه طبق مجوز قبلی کارفرما نامحدود است و در این تغییر بازگردانده نشده است. ریسک سوءاستفادهٔ OTP با تعداد زیاد شماره/نشست نیازمند پایش هزینه، تنظیم مناسب محدودکننده‌های امنیتی و در صورت نیاز ضدربات است؛ ledger، سقف غیرعادی هر تماس، سه هدیه، opt-out و idempotency حفظ شده‌اند.
- این بررسی شامل pentest تهاجمی، اجرای payload روی سرور، تست بار روی سرویس زنده، آزمون از شبکهٔ اینترنت مستقل یا اسکن کامل CVE سیستم‌عامل/لایه‌های image نیست. نسخه‌های runtime مشاهده‌شده: PostgreSQL17.11، Redis7.4.11، RabbitMQ4.4.0 و Node24.20.0. نسخهٔ ظاهری به‌تنهایی نتیجهٔ آسیب‌پذیری نیست؛ image digest و بسته‌های سیستم‌عامل باید جدا اسکن شوند.

### ترتیب انتشار عملیاتی پیشنهادی

1. بکاپ قابل‌بازیابی، کلید فعال/کلیدهای fallback و یک مسیر مدیریت دوم را تأیید کنید. imageها با digest مشخص ثبت شوند؛ تغییر HBA یا SSH نباید تنها مسیر دسترسی اپراتور را ببندد.
2. نقش migration/schema owner و نقش runtime را جدا کنید. runtime به superuser، ساخت role/DB، replication، bypass RLS یا مالکیت جدول نیاز ندارد؛ مجوز جدول/sequence و default privileges مهاجرت‌های بعدی باید صریح تنظیم شوند.
3. SCRAM دیتابیس و ACL/رمز Redis و کاربر/vhost محدود RabbitMQ را همراه تنظیم اتصال سرویس‌ها در candidate آزمایش کنید. فقط بعد از موفقیت اتصال جدید، قواعد `trust` و اعتبارنامه/دسترسی قدیمی حذف شوند. این کار با تغییر env اولیهٔ Docker روی volume موجود، خودکار انجام نمی‌شود.
4. برای migration0017، نویسنده‌ها و worker/beat قدیمی باید از نوشتن/خواندن هم‌زمان کنار گذاشته شوند؛ کد قدیمی بدنهٔ رمز‌شده را نمی‌شناسد. وضعیت‌های درحال ارسال/unknown را حفظ کنید، مهاجرت با کلید موجود و کد جدید اجرا و سپس backend/worker/beat جدید با هم فعال شوند. سفارش لغوشده یا نامعلوم مجوز replay ندارد.
5. rollback به کد قدیمی، نیازمند reverse migration0017 در حالت توقف نویسنده‌ها و با کلیدهای لازم است؛ صرف جایگزینی image قدیمی کافی نیست. reverse، بدنه‌ها را طبق قالب قدیمی متن ساده می‌کند، پس فقط برای بازگشت عملیاتی کنترل‌شده است.
6. frontend دارای nonce و هدرهای امنیتی منتشر شود؛ canonical، متاتگ‌ها، policy مرورگر، دسترسی صاحب داده و صف با بررسی‌های بدون ارسال پیام دوباره تأیید شوند. اعتبارسنجی نصب PWA و آخرین restore دامنهٔ واقعی مستقل باقی می‌مانند.

## اعتبارسنجی و تکرار

در محیط مستقل،۲۹۹تست بک‌اند با PostgreSQL و Redis آزمایشی موفق شدند؛ شامل عدم دسترسی بین کاربران، CSRF، OTP، قفل/رقابت، retry، حذف/نگهداری، کنترل صف، migration0017 رمزنگاری، rollback، چرخش کلید و دسترسی‌های پنل مدیریت جدید. فرانت۳۸تست و TypeScript را گذراند. build مستقل standalone نیز موفق است؛ image یا dev server محصول برای هر ویرایش بازسازی نشده است. بررسی سازگاری migration و تنظیم Compose نیز موفق بود.

اسکن `npm audit` صفر هشدار گزارش کرد. `pip-audit` روی lock قدیمی چهار هشدار و روی lock اصلاح‌شده صفر هشدار شناخته‌شده گزارش کرد. این نتیجه محدود به پایگاه advisory در تاریخ بررسی است.۴۰درخواست بررسی SEO در توسعهٔ HTTPS و۴۰درخواست روی build انتشار مستقل موفق بودند؛ متاتگ‌ها با nonce و canonical صحیح در head باقی مانده‌اند.۱۹درخواست اسکریپت امنیت HTTP نیز جعل nonce/policy، عدم تکرار nonce، عدم cache شدن HTML و عدم انتشار فایل‌های حساس را با موفقیت بررسی کردند. ورود به مرحلهٔ فرم و ناوبری به راهنما در مرورگر production از HTTPS محلی، بدون خطای CSP بررسی شد؛ عرض موبایل۳۷۵پیکسل اسکرول افقی نداشت. ارسال OTP/پیام و پذیرش نصب PWA دامنهٔ واقعی در این بررسی مرورگر انجام نشدند.

بررسی تنظیمات بارشدهٔ یک backend، بدون چاپ secret و بدون تغییر داده:

```sh
python manage.py audit_security --database --redis
```

این فرمان روی همان محیط/تنظیماتی نتیجه می‌دهد که اجرا شده است؛ خروجی محیط محلی، شاهد سرور نیست. `--database` فقط metadata نقش/اتصال و `--redis` فقط PING بدون رمز می‌خواند. برای اجرای آن روی سرور باید کد جدید ابتدا منتشر شده باشد. از helper محلی‌ای که قبل از فرمان `migrate` اجرا می‌کند، برای ادعای بررسی «صرفاً خواندنی» استفاده نکنید.

بررسی frontend production مستقل روی localhost، با مبدأ HTTPS تثبیت‌شده در build:

```sh
python3 scripts/check-security.py --base-url http://127.0.0.1:3101 --expect-hsts
python3 scripts/check-seo.py --base-url http://127.0.0.1:3101 \
  --canonical-origin https://begamnagam.ir --expect-indexable
```

پس از انتشار مجاز، بررسی کامل HTTP:

```sh
python3 scripts/check-security.py --base-url https://begamnagam.ir --expect-hsts --full-stack
```

اسکریپت فقط GET بدون کوکی ارسال می‌کند؛ OTP، پیام، پرداخت و ترجیحات را تغییر نمی‌دهد و بدنه‌ها، کوکی‌ها و nonceها را چاپ نمی‌کند. در development، اجازهٔ eval و websocket برای Fast Refresh وجود دارد؛ اسکریپت محدودیت production را روی dev معیار قرار ندهید.
